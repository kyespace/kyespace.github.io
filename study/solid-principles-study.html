SOLID 원칙 — 변경에 강한 객체지향 설계의 다섯 기둥

다섯 원칙은 결국 하나의 질문으로 수렴한다. "요구사항이 바뀌었을 때, 코드의 어디까지 손대야 하는가?" SOLID는 그 수정 범위를 최소화하기 위한 구조적 장치다.

00

전체 그림 — 왜 SOLID인가Robert C. Martin, 2000s · 객체지향 설계 5원칙

소프트웨어의 비용은 "처음 만드는 비용"보다 "바꾸는 비용"이 지배한다. 요구사항은 반드시 변하고, 변경이 발생할 때마다 코드 전체가 흔들리는 구조라면 유지보수 비용은 기하급수적으로 커진다. SOLID는 변경의 파급 범위를 격리하기 위한 다섯 가지 설계 원칙이다.

다섯 원칙은 독립적인 규칙 나열이 아니라 계층 구조를 이룬다. 아래 지도를 먼저 머리에 넣고 각 원칙을 보면, 개별 원칙이 어느 층을 담당하는지가 보인다.

STRUCTURAL MAP — 각 원칙이 다루는 축
SRP → 클래스 내부
하나의 클래스가 몇 개의 변경 이유를 갖는가. 응집도의 문제.
OCP → 변경 전략
새 요구사항이 올 때 기존 코드를 고치는가, 새 코드를 붙이는가. 확장 구조의 문제.
LSP → 상속 계약
다형성이 실제로 안전한가. 상위 타입의 계약을 하위 타입이 지키는가의 문제.
ISP → 인터페이스 폭
클라이언트가 쓰지도 않는 메서드에 묶여 있는가. 결합 범위의 문제.
DIP → 의존 방향
의존성 화살표가 구체를 향하는가, 추상을 향하는가. 아키텍처 방향의 문제.

읽는 순서 팁 — OCP가 목표(수정 없이 확장)라면, DIP·LSP·ISP는 그 목표를 달성하는 수단이고, SRP는 그 모든 것의 전제 조건이다. 이 관계는 마지막 종합 섹션에서 다시 정리한다.

S

단일 책임 원칙Single Responsibility Principle

"하나의 클래스는 단 하나의 변경 이유만 가져야 한다." — 여기서 '책임'은 기능의 개수가 아니라 변경을 요구하는 액터(actor)의 수다.

흔한 오해는 "클래스는 한 가지 일만 해야 한다"로 읽는 것이다. 정확한 정의는 변경의 이유(reason to change)가 하나여야 한다는 것. 주문 정책이 바뀌어도, 알림 채널이 바뀌어도, 회계 포맷이 바뀌어도 매번 같은 클래스를 열어야 한다면 그 클래스는 세 명의 주인을 섬기고 있는 것이다.

위반 → 개선 예제: 주문 처리 서비스

BAD하나의 클래스에 세 가지 변경 이유가 공존
public class OrderService {

    public void placeOrder(Order order) {
        // [책임 1] 주문 도메인 로직 — 정책 변경 시 수정
        validateStock(order);
        applyDiscount(order);
        orderRepository.save(order);

        // [책임 2] 알림 발송 — 채널(메일→카카오톡) 변경 시 수정
        String html = "<h1>주문 완료</h1>...";
        smtpClient.send(order.getEmail(), html);

        // [책임 3] 정산 기록 — 회계 포맷 변경 시 수정
        String csv = order.getId() + "," + order.getAmount();
        settlementFileWriter.append(csv);
    }
}
▼ 변경 이유별로 분리 ▼
GOOD변경 이유 1개 = 클래스 1개, 조립은 상위에서
public class OrderService {          // 주문 정책만 책임
    private final OrderNotifier notifier;
    private final SettlementRecorder recorder;

    public void placeOrder(Order order) {
        validateStock(order);
        applyDiscount(order);
        orderRepository.save(order);
        notifier.notifyPlaced(order);      // 알림은 위임
        recorder.record(order);            // 정산도 위임
    }
}

public class EmailOrderNotifier implements OrderNotifier { ... }
public class CsvSettlementRecorder implements SettlementRecorder { ... }

이제 알림 채널이 카카오톡으로 바뀌면 KakaoOrderNotifier를 새로 만들 뿐, OrderService는 열지 않는다. 각 클래스의 테스트도 독립적으로 작성할 수 있게 된다.

SRP 위반 신호
  • 클래스 이름에 Manager, Util, Processor처럼 책임이 안 보이는 단어가 들어간다
  • 서로 다른 팀/직군(기획·회계·인프라)의 요청이 같은 클래스 수정으로 이어진다
  • 메서드들이 서로 다른 필드 집합만 사용한다 (응집도 낮음)
  • 단위 테스트 하나를 위해 관계없는 의존성까지 전부 mock해야 한다
SPRING에서는

@Controller / @Service / @Repository 계층 분리 자체가 SRP의 거시적 적용이다 — 요청 처리·비즈니스 규칙·영속성이라는 서로 다른 변경 이유를 계층으로 격리한다.

트랜잭션(@Transactional)이나 로깅을 AOP로 빼내는 것도 SRP의 연장이다. 횡단 관심사를 프록시가 대신 책임지므로 비즈니스 클래스에는 변경 이유가 하나만 남는다.

O

개방-폐쇄 원칙Open-Closed Principle

"확장에는 열려 있고, 수정에는 닫혀 있어야 한다." — 새 기능은 새 코드를 추가해서 구현하고, 검증이 끝난 기존 코드는 건드리지 않는다.

모순처럼 들리는 이 문장의 열쇠는 추상화다. 변하는 부분을 인터페이스 뒤로 숨기면, 새 요구사항은 그 인터페이스의 새 구현체를 추가하는 것으로 흡수된다. 기존 코드는 인터페이스만 바라보므로 재컴파일·재테스트·재배포 위험이 격리된다.

위반 → 개선 예제: 결제 수단 추가

BAD결제 수단이 늘 때마다 if-else 수술
public class PaymentService {
    public void pay(Order order, String method) {
        if (method.equals("CARD")) {
            // 카드 결제 로직
        } else if (method.equals("BANK")) {
            // 계좌이체 로직
        } else if (method.equals("KAKAO_PAY")) {
            // ← 신규 요구사항마다 이 파일을 열고,
            //   기존 분기 전체를 회귀 테스트해야 한다
        }
    }
}
▼ 전략(Strategy) 패턴으로 추상화 ▼
GOOD새 결제수단 = 새 클래스 추가, 기존 코드 무수정
public interface PaymentProcessor {
    boolean supports(PaymentMethod method);
    void pay(Order order);
}

@Component
public class CardPaymentProcessor implements PaymentProcessor { ... }

@Component
public class KakaoPayProcessor implements PaymentProcessor { ... }

@Service
public class PaymentService {
    private final List<PaymentProcessor> processors;  // 스프링이 전부 주입

    public void pay(Order order, PaymentMethod method) {
        processors.stream()
            .filter(p -> p.supports(method))
            .findFirst()
            .orElseThrow(() -> new UnsupportedPaymentException(method))
            .pay(order);
    }
}

네이버페이가 추가돼도 NaverPayProcessor 클래스 하나를 새로 만들면 끝이다. PaymentService는 컴파일조차 다시 할 필요가 없다.

OCP 위반 신호
  • 같은 if-else / switch 분기가 여러 클래스에 중복해서 나타난다
  • "OO 유형 하나 추가해주세요"라는 요청에 수정해야 할 파일이 3개 이상이다
  • 타입 문자열·enum 비교로 동작을 갈라치는 코드가 핵심 로직 안에 있다
SPRING에서는

List<PaymentProcessor>처럼 같은 타입의 빈을 컬렉션으로 주입받는 기능이 OCP 구현의 핵심 도구다. 새 @Component를 추가하는 것만으로 컨테이너가 자동으로 목록에 편입시킨다.

Spring Security의 FilterChainProxy가 필터 목록을 조립하는 방식, HandlerMapping/HandlerAdapter의 확장 구조도 모두 "기존 코드 수정 없이 구현체 추가"라는 OCP 설계다.

L

리스코프 치환 원칙Liskov Substitution Principle

"하위 타입은 상위 타입이 쓰이는 자리에 동작의 변경 없이 치환될 수 있어야 한다." — 상속은 문법이 아니라 계약이다.

컴파일러는 시그니처만 검사한다. LSP는 그 너머, 상위 타입이 암묵적으로 약속한 행동 규약(사전조건·사후조건·불변식)까지 하위 타입이 지켜야 한다고 말한다. 이것이 깨지면 다형성을 믿고 작성한 모든 클라이언트 코드가 잠재적 지뢰밭이 된다.

위반 → 개선 예제: 정사각형은 직사각형인가?

BADis-a처럼 보이지만 계약을 깨는 상속
public class Rectangle {
    protected int width, height;
    public void setWidth(int w)  { this.width = w; }
    public void setHeight(int h) { this.height = h; }
    public int area() { return width * height; }
}

public class Square extends Rectangle {
    @Override public void setWidth(int w)  { width = w; height = w; }
    @Override public void setHeight(int h) { width = h; height = h; }
}

// 클라이언트: Rectangle의 계약("width와 height는 독립")을 믿는다
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;   // Square가 들어오면 16 — 계약 위반!
}
▼ 상속 대신 계약이 맞는 추상화로 ▼
GOOD공통 계약만 추상화하고, 가변 setter는 각자 소유
public interface Shape {
    int area();          // 모든 도형이 안전하게 지킬 수 있는 계약만 노출
}

public class Rectangle implements Shape {
    private final int width, height;
    public Rectangle(int w, int h) { width = w; height = h; }
    public int area() { return width * height; }
}

public class Square implements Shape {
    private final int side;
    public Square(int s) { side = s; }
    public int area() { return side * side; }
}

수학적으로 정사각형은 직사각형이지만, "가로·세로를 독립적으로 바꿀 수 있다"는 행동 계약 안에서는 아니다. is-a 판정은 개념이 아니라 계약으로 해야 한다. 자바 표준 라이브러리의 악명 높은 반례가 java.util.Stack extends Vector다 — 스택인데 중간 삽입이 가능해져 버렸다.

LSP 위반 신호
  • 오버라이드한 메서드가 UnsupportedOperationException을 던진다
  • 클라이언트 코드에 instanceof로 특정 하위 타입을 걸러내는 분기가 있다
  • 하위 클래스가 상위 메서드를 빈 구현(no-op)으로 덮어쓴다
  • 상위 타입보다 사전조건을 강화하거나(더 까다로운 입력 요구) 사후조건을 약화한다
SPRING에서는

컨테이너가 주입하는 빈은 대부분 인터페이스 타입으로 다뤄진다 — PlatformTransactionManager 자리에 DataSourceTransactionManager든 JpaTransactionManager든 치환 가능해야 전체가 동작한다. Spring 생태계 자체가 LSP 위에 서 있는 셈이다.

CGLIB 프록시가 원본 클래스를 상속해 만들어지는 것도 같은 전제다: 프록시는 원본과 행동상 구분 불가능해야 하며, 그래서 final 메서드는 프록시할 수 없다는 제약이 생긴다.

I

인터페이스 분리 원칙Interface Segregation Principle

"클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강제되어서는 안 된다." — 뚱뚱한 인터페이스 하나보다 역할별로 얇은 인터페이스 여럿이 낫다.

SRP가 클래스의 응집도라면 ISP는 인터페이스의 응집도다. 하나의 거대 인터페이스에 여러 클라이언트의 요구를 몰아넣으면, 구현체는 쓰지도 않는 메서드를 억지로 구현해야 하고(→ LSP 위반의 온상), 한 클라이언트의 요구 변경이 무관한 클라이언트까지 재빌드시킨다.

위반 → 개선 예제: 다기능 복합기 인터페이스

BAD모든 기기에 모든 기능을 강요하는 인터페이스
public interface MultiFunctionDevice {
    void print(Document d);
    void scan(Document d);
    void fax(Document d);
}

// 보급형 프린터: 인쇄만 되는데 전부 구현해야 한다
public class BasicPrinter implements MultiFunctionDevice {
    public void print(Document d) { /* OK */ }
    public void scan(Document d)  { throw new UnsupportedOperationException(); }
    public void fax(Document d)   { throw new UnsupportedOperationException(); }
}   // ← ISP 위반이 곧바로 LSP 위반으로 번지는 전형적 패턴
▼ 역할(role) 단위로 분리 ▼
GOOD필요한 역할만 골라 구현·의존
public interface Printer { void print(Document d); }
public interface Scanner { void scan(Document d); }
public interface Fax     { void fax(Document d); }

public class BasicPrinter implements Printer { ... }

public class OfficeMachine implements Printer, Scanner, Fax { ... }

// 클라이언트도 필요한 역할에만 의존한다
public class ReportGenerator {

}
ISP 위반 신호
  • 구현체 곳곳에 빈 메서드나 UnsupportedOperationException이 있다
  • 인터페이스 메서드가 10개를 넘고, 구현체마다 실제 쓰는 부분집합이 다르다
  • 인터페이스에 메서드 하나를 추가했더니 무관한 구현체 전부가 컴파일 에러를 낸다
SPRING에서는

빈 생명주기 콜백이 좋은 예다 — InitializingBean, DisposableBean, BeanNameAware가 하나의 거대 인터페이스가 아니라 콜백별로 잘게 쪼개져 있어 필요한 것만 선택 구현한다.

Spring Data의 Repository 계층도 마찬가지: CrudRepository → PagingAndSortingRepository → JpaRepository로 역할을 누적하는 구조라, 읽기 전용 저장소는 상위의 얇은 인터페이스만 노출하는 식의 통제가 가능하다.

D

의존성 역전 원칙Dependency Inversion Principle

"고수준 모듈은 저수준 모듈에 의존해서는 안 된다. 둘 다 추상화에 의존해야 한다." — 의존성 화살표를 세부사항이 아닌 정책 쪽으로 뒤집는다.

전통적 절차 구조에서는 정책(비즈니스 규칙)이 세부사항(DB, 외부 API, 파일)에 의존한다. DB 벤더를 바꾸면 비즈니스 코드가 흔들리는 이유다. DIP는 이 방향을 뒤집는다 — 정책이 인터페이스를 소유하고, 세부사항이 그 인터페이스를 구현하러 온다. "역전(inversion)"이라는 이름은 이 화살표 방향의 반전을 가리킨다.

위반 → 개선 예제: 알림 발송 의존성

BAD고수준(주문 정책)이 저수준(SMTP 구현)을 직접 생성·의존
public class OrderService {

    public void placeOrder(Order order) {
        // ... 주문 로직 ...
        sender.sendEmail(order.getEmail(), "주문 완료");
        // 문제 1: 카카오톡 알림으로 못 바꾼다 (코드 수술 필요)
        // 문제 2: 테스트 시 실제 SMTP 서버가 필요하다
    }
}

public interface NotificationSender {

@Service
public class OrderService {

주의할 구분 — DIP는 원칙, DI(의존성 주입)는 기법, IoC 컨테이너는 도구다. DIP가 "추상에 의존하라"는 방향을 제시하면, DI는 그 추상의 구현체를 외부에서 꽂아주는 방법이고, Spring 컨테이너는 그 꽂아주는 일을 자동화하는 프레임워크다. 세 용어는 층위가 다르다.

DIP 위반 신호
  • 비즈니스 클래스 안에 new 구체클래스()가 직접 등장한다
  • 도메인 코드가 특정 벤더 SDK·드라이버 클래스를 import한다
  • 단위 테스트가 DB·네트워크 없이는 실행되지 않는다
  • 모듈 의존 그래프에서 화살표가 안정적인 것 → 변덕스러운 것 방향으로 흐른다

IoC 컨테이너의 존재 이유 그 자체다. 빈 정의를 읽어 객체 그래프를 조립하고 생성자 주입으로 꽂아주는 전 과정이 "구체 생성의 책임을 애플리케이션 코드에서 컨테이너로 역전"시킨 것이다.

DataSource, PlatformTransactionManager, CacheManager 같은 포트 인터페이스에 코드를 작성하고 구현체는 설정으로 갈아끼우는 Spring의 일관된 관례가 곧 DIP의 실천이다.

다섯 원칙의 역학 관계

SOLID는 다섯 개의 독립 규칙이 아니라 하나의 목표를 향한 협력 구조다.

RELATIONSHIP MAP
목표: OCP
"수정 없이 확장한다"가 SOLID 전체가 지향하는 상태다.
수단: DIP
추상화에 의존해야 구현체를 갈아끼울 수 있다 — OCP의 구조적 토대.
보증: LSP
치환이 안전해야 DIP의 "갈아끼우기"가 실제로 동작한다 — 다형성의 품질 보증.
정밀화: ISP
추상화가 얇고 역할 중심이어야 LSP를 지키기 쉽고 결합 범위가 최소화된다.
전제: SRP
책임이 뒤엉킨 클래스에서는 위 네 원칙을 적용할 단위 자체가 성립하지 않는다.

  • 새 유형·정책 추가 요구가 왔다고 가정할 때, 추가되는 파일 수 > 수정되는 파일 수인가?
  • 모든 오버라이드 메서드가 상위 타입의 시그니처뿐 아니라 기대 행동까지 지키는가?
  • 인터페이스의 모든 메서드를 모든 구현체가 의미 있게 구현하고 있는가?
  • 도메인·서비스 계층에서 인프라 구체 클래스 import가 0건인가?
  • 이 클래스의 단위 테스트를 외부 시스템 없이 작성할 수 있는가? (다섯 원칙 준수의 종합 리트머스)

마지막 주의 — SOLID는 법이 아니라 트레이드오프 도구다. 변경 가능성이 낮은 코드에 추상화를 선제 도입하면 오히려 간접 계층만 늘어난다(과잉 설계). 원칙을 적용하는 기준은 언제나 "이 지점에 실제로 변경 압력이 존재하는가"이다.
