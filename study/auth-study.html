AUTHENTICATION STUDY NOTES

폼 로그인 vs OAuth2 로그인

같은 목적("이 사람이 누구인지 확인한다")을 전혀 다른 방식으로 푸는 두 가지 인증 방식을 흐름 단위로 뜯어본다. 누가, 무엇을, 누구에게 증명하는지가 핵심이다. 밑줄 친 약어는 눌러서 설명을 볼 수 있다.

세션 기반 · 신뢰 주체 = 우리 서버 토큰 기반 · 신뢰 주체 = 외부 IdP
01 · Session

폼 로그인 (Form-based Login)

아이디/비밀번호를 서버에 직접 제출하고, 서버가 세션을 발급해 로그인 상태를 유지하는 가장 전통적인 방식. 인증 주체가 우리 서버 자신이라는 점이 핵심이다.

인증 흐름
1
브라우저 → 서버
로그인 폼에 아이디/비밀번호를 입력하고 POST /login 요청을 보낸다.
2
서버 → DB
DB에서 사용자를 조회하고, 저장된 password_hash와 입력값을 해시 비교(bcrypt 등)한다. 평문 비교는 절대 하지 않는다.
3
서버
인증 성공 시 세션을 생성하고 세션 저장소(메모리, Redis 등)에 session_id → 사용자 정보를 저장한다.
4
서버 → 브라우저
응답 헤더에 Set-Cookie: SESSION=xxx; HttpOnly; Secure를 담아 세션 쿠키를 내려준다.
5
브라우저 → 서버 (이후 모든 요청)
브라우저가 쿠키를 자동으로 실어 보내고, 서버는 세션 저장소를 조회해 로그인 상태를 판별한다.

▲ 장점

  • 구현이 단순하고 개념적으로 직관적이다
  • 서버가 세션을 완전히 통제한다 — 강제 로그아웃, 즉시 무효화가 쉽다
  • 외부 서비스 의존성이 없어 장애 지점이 적다
  • 토큰 탈취 시나리오가 상대적으로 단순해 대응하기 쉽다

▼ 단점

  • 서버가 상태(state)를 가져야 해서 수평 확장 시 세션 클러스터링/공유 스토어가 필요
  • CSRF 방어(토큰, SameSite 쿠키)를 직접 신경 써야 한다
  • 모바일 앱·SPA 등 쿠키를 다루기 애매한 환경에서 불편
  • 여러 서비스 간 SSO(Single Sign-On) 구현이 번거롭다
  • 비밀번호를 우리가 직접 저장·관리해야 하는 책임이 생긴다
엣지 케이스 — SPA와 궁합이 안 맞는 이유
1
배포 구조
SPA 프론트엔드는 app.myservice.com(또는 Vercel/Netlify 같은 별도 호스팅), API 서버는 api.myservice.com처럼 서로 다른 도메인에 배포되는 경우가 흔하다.
2
로그인 성공
로그인 요청은 성공하고 서버가 Set-Cookie: SESSION=xxx를 응답에 담아 보낸다 — 여기까지는 문제없다.
3
⚠️ 바로 다음 요청부터 문제 발생
브라우저 쿠키 기본값인 SameSite=Lax 정책 때문에, SPA가 그 직후 보내는 fetch/XHR 요청에는 쿠키가 자동으로 실리지 않는다. 방금 로그인했는데도 API는 "로그인 안 된 사용자"로 취급한다.
4
고친다고 해도
쿠키를 SameSite=None; Secure로 바꾸고, CORS에서 Access-Control-Allow-Credentials: true와 정확한 Origin을 지정하고, 프론트의 모든 요청에 credentials: 'include'를 빠짐없이 넣어야 한다 — 설정 지점이 4곳으로 늘어난다.
5
그렇게 다 맞춰도
Safari의 ITP, 크롬 시크릿 모드의 서드파티 쿠키 차단 정책 때문에 일부 브라우저·모드에서는 여전히 로그인이 풀린다. 서버 설정만으로는 완전히 해결되지 않는 영역이 남는다.
그래서 실무에서는 — 프론트/API가 도메인을 공유하지 않는 SPA 구조에서는 세션 쿠키 대신, 로그인 응답으로 access_token을 바디에 받아 프론트가 메모리에 들고 있다가 매 요청마다 Authorization: Bearer <token> 헤더로 직접 실어 보내는 토큰 기반 방식을 흔히 택한다. 쿠키의 자동 전송에 기대지 않으므로 SameSite·CORS 자격 증명 문제 자체가 사라진다.

실무 활용 예시

사내 관리자(Admin) 페이지 전통적인 SSR 웹앱 Spring Security formLogin() Django / Rails 기본 auth 폐쇄망·내부 시스템
02 · Token / Delegated

OAuth2 로그인 (Authorization Code + PKCE)

엄밀히 OAuth2는 인가(authorization) 프로토콜이다. 여기에 OpenID Connect(OIDC)가 얹혀 신원 확인용 id_token을 제공하면서 비로소 "로그인"에 쓰인다. 인증 주체는 외부 IdP(구글, 카카오 등)다.

동작 흐름 다이어그램
프론트채널 (브라우저 경유) 백채널 (서버-서버 직접 통신)
단계별 상세 설명
1
브라우저 → 우리 서버
"구글로 로그인" 버튼 클릭. 서버는 code_verifier를 생성하고 그 해시값인 code_challenge를 준비한다(PKCE).
2
브라우저 → Authorization Server(구글)
client_id, redirect_uri, scope, state, code_challenge를 담아 구글 인증 페이지로 리다이렉트된다.
3
사용자 ↔ 구글
사용자가 구글 계정으로 로그인하고, 우리 앱에 정보 제공을 동의(consent)한다.
4
구글 → 브라우저 → 서버
구글이 redirect_uri로 1회용 authorization code와 state를 실어 리다이렉트한다.
5
서버 → 구글 (백채널)
서버가 code + code_verifier + client_secret을 토큰 엔드포인트로 보내 토큰 교환을 요청한다.
6
구글 → 서버
access_token, id_token(OIDC, JWT), refresh_token을 발급받는다.
7
서버
id_token의 서명·iss·aud·exp를 검증해 사용자 신원(이메일 등)을 확정한다.
8
서버 → 브라우저
확인된 사용자로 자체 세션 또는 자체 JWT를 발급하며 로그인이 완료된다.
id_token vs access_token — 발급 주체는 같지만 역할이 다르다

Q. 이 두 토큰은 실제로 같은 OAuth2 인증 서버(Authorization Server)가 발급하는 것인가요, 아니면 서로 다른 곳에서 발급되는 것인가요?

A. 두 토큰 모두 같은 Authorization Server(구글)가, 위 다이어그램의 9번 단계(토큰 응답)에서 함께 발급합니다. 발급 시점과 발급 주체는 완전히 동일하며, 누가 그 토큰을 읽고 신뢰해야 하는가(소비 주체)만 다릅니다.

▲ 장점

  • 비밀번호를 우리가 저장하지 않는다 — 유출 책임과 위험을 IdP에 위임
  • 원클릭 로그인으로 회원가입 이탈률이 낮다
  • IdP가 MFA·이상 로그인 탐지를 대신 처리해 준다
  • SSO·여러 서비스 간 신원 공유가 자연스럽다

▼ 단점

  • 외부 IdP 장애 시 우리 서비스 로그인도 함께 막힌다
  • 리다이렉트, state, PKCE 등 보안 디테일이 많아 구현·검증이 복잡
  • 토큰 저장·만료·갱신(refresh) 로직을 별도로 관리해야 한다
  • redirect_uri 오설정 등 실수 하나가 심각한 보안 취약점이 될 수 있다

실무 활용 예시

구글/카카오/네이버 소셜 로그인 사내 SSO — Okta, Auth0, Keycloak 모바일 앱 소셜 로그인 서비스 간 API 인가 (Client Credentials Flow) "제3자 앱에 캘린더 접근 허용" 같은 위임 인가
DEEP-DIVE access_token은 언제, 어디로 오가는가

로그인이 끝난 뒤 애플리케이션을 사용하는 동안, 실제로는 성격이 다른 두 종류의 통신이 동시에 존재한다. 이 둘을 구분해서 보면 흐름이 훨씬 명확해진다.

FE (브라우저 / 앱)
우리 시스템이 발급한 세션 쿠키 또는 JWT
빈도 — 우리 서버로 보내는 모든 요청마다

화면 조회, 데이터 저장 등 애플리케이션 내부의 통상적인 기능은 전부 이 경로로 처리된다. access_token은 이 구간에 전혀 관여하지 않는다. 로그인 수단이 무엇이었든(폼 로그인이든 OAuth2든), 이 구간은 폼 로그인의 세션 쿠키 방식과 완전히 동일하게 동작한다.

BE (우리 서버)
access_token
빈도 — 구글 소유 리소스가 필요한 요청에서만

캘린더 조회, 메일 전송처럼 구글이 소유한 리소스를 다뤄야 할 때만, BE가 보관해둔 access_token을 꺼내 구글 API를 호출한다.

구글 리소스 서버 (Calendar API 등)

scope 판단은 왜 구글의 몫인가

access_token이 담는 권한(scope)은 우리 애플리케이션 내부의 세부 권한이 아니라 구글이 소유한 리소스에 대한 접근 권한이다. 우리는 등록 시 사용할 scope를 선언하고 로그인 요청에 명시할 뿐이며, 그 scope가 실제로 유효한지는 리소스를 소유한 구글이 판단하고 사용자가 동의 화면에서 승인해야 발급된다. "이 사용자가 우리 앱의 관리자인가" 같은 판단은 구글이 관여하지 않는 별개의 인가 로직으로, 로그인 완료 후 우리 시스템이 자체 DB로 직접 결정한다.

왜 매번 다시 증명해야 하는가

구글의 리소스 서버는 우리 애플리케이션과 세션을 공유하지 않는 별도의 시스템이다. 건물에 한 번 등록됐다고 문마다 카드를 안 대는 게 아니라 매번 태그해야 하듯, 구글 API도 요청마다 access_token으로 자격을 증명해야 한다. 덕분에 사용자가 연결을 해제하면 다음 요청부터 즉시 차단되고, 토큰 수명을 짧게 유지해 유출 시 피해도 최소화된다. refresh_token은 이 짧은 access_token을 재로그인 없이 갱신하기 위한 장치다.

나중에 필요해졌을 때 — access_token이 만료돼 있다면

access_token은 보통 수십 분~1시간 정도로 짧게 만료된다. 로그인 직후엔 안 쓰다가 한참 뒤에 구글 캘린더 기능을 실제로 호출하는 시점엔, 그 access_token은 이미 만료돼 있을 가능성이 높다. 이 상황은 예외가 아니라 기본적으로 예정된 흐름이다.

1
사용 시점 도래
사용자가 실제로 구글 캘린더 기능을 눌렀다. BE는 API를 호출하기 직전에 보관 중인 access_token의 만료 여부를 확인한다.
2
✅ 아직 유효한 경우
그대로 access_token을 실어 구글 API를 호출한다. 별도 절차 없음.
3
⏰ 만료된 경우 — BE ↔ 구글 (백채널)
BE가 보관해둔 refresh_token으로 구글 토큰 엔드포인트에 재발급을 요청한다. 사용자 개입도, 재로그인도 없이 새 access_token을 즉시 받는다.
4
🛑 refresh_token까지 만료·철회된 경우
이때만 예외적으로 사용자를 다시 구글 동의 화면으로 보내 처음부터 인가를 다시 받는다. (오랜 미사용, 사용자의 수동 연결 해제, 비밀번호 변경 등으로 발생)
핵심 — access_token의 짧은 수명 자체는 문제가 되지 않는다. 쓰기 직전에 유효성을 확인하고, 필요하면 그 순간 조용히 갈아 끼우기 때문이다. refresh_token이 존재하는 이유가 정확히 이 "오래 안 쓰다가 나중에 쓰는" 시나리오를 대비하기 위함이다.
그렇다면 애초에 access_token 하나를 길게 두면 안 되나

기술적으로는 가능하지만, 노출 빈도와 위험이 다른 두 가지 역할을 하나의 토큰에 억지로 합치는 셈이라 손해가 더 크다. access_token과 refresh_token을 분리하면 각자의 위험 수준에 맞춰 서로 다른 전략을 적용할 수 있다.

비교 항목access_token 하나만, 길게access_token(짧게) + refresh_token
노출 빈도매 API 요청마다 네트워크로 노출access_token만 매 요청 노출 · refresh_token은 갱신 시점에만 극히 드물게 노출
유출 시 피해 범위만료 전까지 장시간 전체 접근 허용access_token이 유출돼도 곧 만료되어 피해 창이 짧음
즉시 차단(revocation)자체 검증 토큰이라 만료 전엔 막을 방법이 마땅치 않음만료 주기가 짧아 다음 재확인 시점에 사실상 즉시 차단됨
보관 위치민감한 장수명 토큰을 여러 경로로 들고 다녀야 함refresh_token은 BE에만 안전하게 보관, access_token만 짧게 순환
사용자 경험재로그인은 없지만 위 위험을 그대로 감수재로그인 없이 조용히 갱신되어 경험은 동일하게 유지
비유 — access_token은 발레파킹 키다. 자주 남에게 건네고, 짧은 시간만 쓰이고, 잃어버려도 할 수 있는 일이 제한적이다. refresh_token은 집 안 금고에 넣어두는 원본 키다. 거의 꺼내지 않고, 남에게 건넬 일도 없으며, 오직 새 발레파킹 키를 만들 때만 쓰인다. 이렇게 노출 빈도가 다른 두 가지 위험을 분리하는 것이 access_token을 그냥 길게 두는 것보다 훨씬 안전하다.
03 · Deep-dive

code_verifier / code_challenge는 실제로 어떻게 동작할까

인가 코드(authorization code)는 리다이렉트 URL에 그대로 노출되기 때문에, 브라우저 히스토리·프록시 로그·악성 앱 등을 통해 중간에 가로채일 가능성이 있다. PKCE는 "코드를 훔쳐도 토큰으로 바꿀 수 없게" 만드는 장치다. 아래에서 직접 값을 생성해보며 원리를 확인해보자.

동작 원리 3단계
1
클라이언트 (요청 시작 시)
무작위 code_verifier(43~128자)를 만들어 클라이언트 메모리에만 보관한다. 이 값은 네트워크로 전송되지 않는다.
2
클라이언트 → 인증 서버 (1차 요청)
code_verifier를 SHA-256으로 해시하고 Base64URL로 인코딩한 code_challenge만 인가 요청에 실어 보낸다. 해시는 역산이 사실상 불가능하므로, 이 값만 봐서는 원본을 알 수 없다.
3
클라이언트 → 인증 서버 (토큰 교환)
인가 코드와 함께 원본 code_verifier를 제출한다. 인증 서버는 저장해둔 code_challenge와 SHA256(code_verifier)를 비교해 같은 클라이언트가 시작부터 끝까지 요청했는지를 검증한다.
직접 만들어보는 PKCE 데모
브라우저에서 실제 SHA-256 연산으로 계산됩니다
code_verifier 클라이언트만 보관 · 절대 전송되지 않음
버튼을 눌러 생성하세요
↓ SHA-256(code_verifier) → Base64URL 인코딩
code_challenge 1차 인가 요청에 실려 서버로 전송됨
—

✅ 우리 서버가 토큰을 교환할 때

2단계에서 받아둔 code_challenge와, 3단계에서 우리 서버가 제출한 진짜 code_verifier를 해시해서 비교한다.

SHA256(우리가 제출한 code_verifier) = — 일치 → 토큰 발급 ✅

🛑 공격자가 코드만 훔쳤을 때

공격자는 authorization code는 가로챘지만 code_verifier는 원 클라이언트 메모리에만 있어 알 수 없다. 임의로 값을 지어내 제출해본다.

SHA256(공격자가 지어낸 값) = — 불일치 → 토큰 발급 거부 ❌
핵심 — code_challenge는 "잠긴 상자"이고 code_verifier는 그 "열쇠"다. 인가 코드가 도중에 유출돼도, 공격자는 열쇠(code_verifier)를 만든 적이 없으므로 최종 토큰 교환 단계를 통과하지 못한다.
04 · Air-gapped

폐쇄망 환경에서 OAuth2 적용하기

인터넷이 차단된 사내망·공공기관·금융권 등에서는 구글·카카오 같은 외부 IdP에 접근할 수 없다. 이때도 OAuth2/OIDC의 프로토콜 구조 자체는 그대로 두고, Authorization Server를 내부에 직접 세우는 것이 일반적인 접근이다.

일반적인 적용 절차
1
인프라
사내 Authorization Server를 구축한다. Keycloak, WSO2 Identity Server, Gluu 등 OIDC 호환 오픈소스(또는 상용 IAM)를 폐쇄망 내부에 설치해 "우리만의 구글"을 만든다.
2
계정 연동
사내 AD/LDAP, HR 시스템의 사번 계정을 Authorization Server와 연동한다. 사용자용 계정 체계를 별도로 새로 만들지 않는다.
3
TLS/DNS
외부 CA(Let's Encrypt 등)에 접근할 수 없으므로 사내 루트 인증서로 사설 TLS 인증서를 발급하고, authorize·token·jwks 등 엔드포인트를 내부 DNS 존(예: sso.internal.corp)으로 구성한다.
4
클라이언트 등록
각 사내 서비스를 클라이언트로 등록하고 redirect_uri를 지정한다. JWT 서명 검증용 공개키(JWKS)는 외부 fetch 없이 내부망에서 주기적으로 캐싱·동기화한다.
5
플로우 적용
브라우저 리다이렉트, 인가 코드 교환, 토큰 검증 등 표준 Authorization Code + PKCE 흐름을 공개 인터넷 환경과 동일하게 그대로 적용한다.
6
선택 사항
서비스 간(server-to-server) 통신에는 client_credentials 플로우에 mTLS를 병행해, 폐쇄망 특유의 강한 신원 검증 요구를 충족시킨다.
핵심 요약 — 프로토콜(리다이렉트 → 코드 발급 → 토큰 교환 → 검증)은 그대로 두고, 신뢰 루트(Authorization Server)의 위치만 외부에서 내부로 옮기는 것이 폐쇄망 OAuth2 적용의 본질이다. 완전 폐쇄가 아니라 특정 IdP 도메인만 프록시로 화이트리스트 허용하는 제한적 아웃바운드 방식을 쓰는 경우도 있다.

실무 활용 예시

Keycloak / WSO2 Identity Server 자체 구축 사내 SSO 게이트웨이 금융·공공기관 내부망 인증 서비스 메시 내 mTLS + Client Credentials 사번 계정 기반 AD/LDAP 연동 로그인

실무에서는 대부분 두 방식을 같이 쓴다

흔한 패턴은 폼 로그인 + 소셜 로그인 병행이다. 이메일/비밀번호 가입도 열어두고, 구글·카카오 버튼도 함께 제공한 뒤, 어떤 경로로 로그인했든 최종적으로는 우리 서버가 발급하는 세션이나 JWT로 통일해서 이후 요청을 처리한다. 즉, OAuth2는 "누구인지 확인하는 단계"에서만 쓰이고, 그 이후의 인가·세션 관리는 결국 우리 시스템의 몫이다.

정리하면: 인증 수단은 다양해질 수 있어도, 인증 이후의 상태 관리는 서비스가 직접 설계해야 한다는 점은 변하지 않는다.
