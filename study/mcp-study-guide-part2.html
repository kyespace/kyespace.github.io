01 · TRANSPORT INTERNALS

Streamable HTTP 내부 — 세션, SSE, 재개

Part 1에서 "원격은 Streamable HTTP"라고 한 문장으로 지나갔던 것을 열어봅니다. 핵심은 단일 엔드포인트 위에서 요청-응답과 서버발 스트림을 동시에 처리하는 방식입니다.

동작 규칙

  • 서버는 엔드포인트 하나(관례상 /mcp)만 노출하고, 클라이언트의 모든 JSON-RPC 메시지는 이곳으로 HTTP POST됩니다
  • 서버는 각 POST에 두 가지 방식으로 응답할 수 있습니다 — 단답이면 Content-Type: application/json으로 즉시 응답, 진행 통지·중간 메시지가 필요하면 text/event-stream으로 전환해 SSE 스트림으로 여러 메시지를 흘려보낸 뒤 최종 응답으로 마감
  • 클라이언트는 별도의 HTTP GET으로 대기용 스트림을 열어둘 수 있습니다 — 서버가 요청과 무관하게 보내는 통지(tools/list_changed 등)를 받는 채널

여기서 Part 1의 "MCP는 stateful 세션"이라는 명제가 HTTP라는 stateless 전송 위에서 어떻게 구현되는지가 보입니다 — 세션 ID 헤더가 상태의 열쇠이고, 이는 서블릿 컨테이너가 JSESSIONID 쿠키로 HttpSession을 복원하는 것과 정확히 같은 패턴입니다. 다만 쿠키가 아닌 명시적 헤더라는 점, 그리고 스케일아웃 시 세션 저장소(Redis 등)나 sticky routing이 필요해진다는 함의도 동일하게 따라옵니다.

끊긴 스트림의 재개 (Resumability)

SSE 스트림의 각 이벤트에 서버가 id: 필드를 붙여두면, 네트워크가 끊긴 클라이언트는 재접속 시 Last-Event-ID 헤더로 "여기까지 받았다"를 알릴 수 있고, 서버는 그 이후 메시지만 재전송합니다. 장시간 도는 도구(대량 스캔, 빌드)를 원격 서버에 두려면 이 재개 지원 여부가 실질적인 안정성을 좌우합니다 — SDK가 대부분 처리해주지만, 프록시/로드밸런서가 SSE를 버퍼링하거나 idle timeout으로 끊지 않는지는 인프라 쪽에서 직접 챙겨야 하는 부분입니다.

실무 노트 — 리버스 프록시 뒤의 SSE

Nginx 뒤에 MCP 서버를 두면 기본 설정이 SSE를 망가뜨리는 경우가 많습니다. proxy_buffering off, 충분한 proxy_read_timeout, HTTP/1.1 + Connection "" 설정이 없으면 "도구가 오래 걸리면 응답이 안 와요" 류의 장애가 됩니다. 증상만 보면 서버 버그처럼 보이는데 원인은 프록시 버퍼링인, 전형적인 계층 착시 사례입니다.

02 · AUTHORIZATION

인증 — OAuth 2.1과 Resource Server로서의 MCP

원격 서버를 띄우는 순간 "누가 이 도구를 호출할 수 있는가"가 프로토콜 문제가 됩니다. 2025-06-18 스펙의 답은 명확합니다 — MCP 서버는 OAuth 2.1의 Resource Server다.

역할 분리가 핵심

초기 스펙은 MCP 서버가 인가 서버(Authorization Server) 역할까지 겸하는 모양이었지만, 현행 스펙은 이를 분리했습니다. MCP 서버는 토큰을 발급하지 않고 검증만 합니다. 토큰 발급은 기존 IdP(Keycloak, Okta, 사내 SSO)가 담당합니다. 즉 여러분이 만드는 서버에 로그인 화면을 구현할 필요가 없습니다.

CLIENT (호스트)
MCP SERVER (RS)
AUTH SERVER (IdP)
──▶
토큰 없이 요청
클라이언트가 일단 /mcp에 POST
◀──
401 + WWW-Authenticate
헤더에 Protected Resource Metadata 위치 안내 → 클라이언트가 /.well-known/oauth-protected-resource를 읽어 "어느 인가 서버에서 토큰을 받아야 하는지" 발견
OAuth
클라이언트 ↔ IdP 사이에서 표준 Authorization Code + PKCE 플로우 진행 (브라우저 열림 → 사용자 로그인·동의 → 토큰 발급). 사전 등록이 없다면 Dynamic Client Registration으로 자동 등록
──▶
Authorization: Bearer <token>
이후 모든 MCP 요청에 토큰 첨부. 서버는 서명·만료·audience를 검증
Audience 검증이 왜 강조되는가 — Confused Deputy 차단

스펙이 유독 힘주어 요구하는 것이 "토큰의 audience가 이 MCP 서버인지 검증하고, 받은 토큰을 뒤단 API로 그대로 전달(passthrough)하지 말 것"입니다. Jira용으로 발급된 토큰을 들고 온 클라이언트에게 Nexus 작업을 해주는 순간, 서버가 권한 없는 요청의 대리인(confused deputy)이 되기 때문입니다. 뒤단 호출이 필요하면 서버 자신의 자격증명이나 token exchange로 별도 토큰을 써야 합니다. Part 1 보안 장의 위협 모델이 여기서 프로토콜 규칙으로 구체화됩니다.

실무 노트 — 폐쇄망의 현실적 타협

내부망 전용 서버에서 풀 OAuth가 과할 때 실무에서는 (a) mTLS + 네트워크 ACL, (b) 정적 Bearer 토큰(서비스 계정 단위) 같은 축약형을 쓰기도 합니다. 다만 이 경우 "누가 무슨 도구를 호출했는가"의 사용자 단위 감사 추적을 포기하는 것이므로, 금융권 감사 요건이 있다면 처음부터 사내 IdP 연동으로 가는 편이 재작업을 줄입니다.

03 · CLIENT-SIDE PRIMITIVES

역방향 프리미티브 — Sampling · Elicitation · Roots

Part 1에서 이름만 소개했던, 서버 → 클라이언트 방향의 요청들입니다. 이것들을 이해하면 "서버는 수동적 응답기"라는 그림이 "서버도 대화의 참여자"로 확장됩니다.

Sampling — 서버가 지능을 빌려 쓰는 방법

서버가 sampling/createMessage 요청을 클라이언트로 보내면, 클라이언트(호스트)가 자기 LLM으로 추론을 수행해 결과를 돌려줍니다. 서버 입장의 의미가 큽니다 — API 키 없이, 어느 모델인지도 모른 채 LLM 능력을 쓸 수 있습니다. 비용과 모델 선택권은 호스트 사용자에게 남습니다.

FastMCP — 도구 안에서 sampling 사용python
@mcp.tool()
async def summarize_incident_log(path: str, ctx: Context) -> str:
    """장애 로그 파일을 읽어 핵심 타임라인을 요약합니다."""
    raw = read_log(path, max_bytes=200_000)
    result = await ctx.session.create_message(          # ← 서버→클라이언트 역요청
        messages=[SamplingMessage(role="user",
            content=TextContent(type="text",
                text=f"다음 로그에서 장애 타임라인을 5줄로 요약:\n{raw}"))],
        max_tokens=500)
    return result.content.text

주의할 점: 호스트가 sampling capability를 선언한 경우에만 쓸 수 있고, 호스트는 요청을 사용자 승인 대상으로 취급할 수 있습니다. 실제 호스트 지원 편차가 커서, sampling에 핵심 로직을 의존하는 서버는 지원 안 되는 호스트에서의 폴백을 함께 설계해야 합니다.

Elicitation — 실행 중간에 사용자에게 묻기

도구 실행 도중 서버가 구조화된 스키마와 함께 "추가 입력이 필요하다"고 요청하면, 호스트가 사용자에게 폼/질문을 띄워 답을 회수해 돌려줍니다. 사용자는 수락 외에 거절(decline)과 취소(cancel)를 선택할 수 있고 서버는 세 경우를 모두 처리해야 합니다. "인자를 미리 다 받는 대신, 필요해진 시점에 묻는" 대화형 도구가 가능해지는 메커니즘입니다 — 예컨대 티켓 생성 도구가 프로젝트 키가 모호할 때 후보를 제시하고 고르게 하는 식입니다.

Roots — 작업 경계의 선언

클라이언트가 서버에게 파일시스템 URI 목록을 알려주는 메커니즘입니다. "이 프로젝트 디렉터리들 안에서 작업하라"는 가이드라인이며, 강제 샌드박스가 아닙니다 — 실제 격리는 OS 권한·컨테이너로 별도 확보해야 합니다. 잘 만든 파일시스템 계열 서버는 roots 변경 통지(roots/list_changed)를 구독해 작업 범위를 동적으로 갱신합니다.

04 · OPERATIONAL MESSAGES

운용 메시지 — Progress · Cancellation · Logging · Pagination

데모 서버와 프로덕션 서버의 차이는 대부분 이 장에 있습니다. 오래 걸리는 작업, 중단, 관측, 큰 목록을 프로토콜이 어떻게 다루는지.

메커니즘동작실무 포인트
Progress 요청에 progressToken이 있으면 서버가 notifications/progress로 진행률(progress/total/message)을 스트리밍 수십 초 넘는 도구는 필수 — 진행 통지가 없으면 호스트·프록시 타임아웃으로 오인 종료됨. FastMCP에선 ctx.report_progress()
Cancellation notifications/cancelled로 진행 중 요청 취소 통지. 응답은 오지 않을 수 있음 통지는 "요청"일 뿐 — 서버 코드가 취소를 체크하지 않으면 백그라운드 작업은 계속 돕니다. 긴 루프에 취소 체크포인트를 심을 것
Logging 서버가 notifications/message로 구조화된 로그(level: debug~emergency)를 클라이언트에 전송. 클라이언트는 logging/setLevel로 수위 조절 stdio의 stderr 로그(사람용)와 별개인 프로토콜 내 로그 채널. Inspector의 Notifications 탭에서 보이는 것이 이것
Pagination tools/list·resources/list 등 목록 응답에 nextCursor — 있으면 그 커서로 재요청 커서는 불투명(opaque) 토큰 — 클라이언트가 파싱·재조립하면 안 됨. 직접 클라이언트를 만들 때(7장) 커서 루프 누락이 흔한 버그
Ping 양방향 ping 요청으로 생존 확인 유휴 세션 정리 정책과 함께 설계 — 어느 쪽이 얼마나 자주 보낼지는 구현 재량
타임아웃의 3중 구조

원격 MCP에서 "느린 도구"가 죽는 경로는 세 겹입니다 — ① 호스트의 도구 실행 타임아웃, ② 프록시/LB의 idle timeout, ③ 서버 자체의 요청 타임아웃. progress 통지는 ①을 리셋시키는 표준 수단이고(스펙이 이를 명시적으로 허용), ②는 인프라 설정, ③은 서버 구현 문제입니다. 장애 분석 시 어느 겹에서 끊겼는지부터 특정하세요.

05 · STRUCTURED OUTPUT

Structured Output과 Context 객체

2025-06-18 스펙의 실질적 개선 — 도구가 "모델이 읽을 텍스트"와 "프로그램이 쓸 구조화 데이터"를 함께 반환할 수 있게 됐습니다.

outputSchema와 structuredContent

도구 정의에 outputSchema(JSON Schema)를 선언하면, 결과에 structuredContent 필드로 스키마를 따르는 JSON을 실을 수 있습니다. 기존 content(텍스트)는 하위 호환을 위해 함께 반환합니다. 의미가 큰 지점은 에이전트 파이프라인입니다 — 도구 A의 출력을 도구 B의 입력으로 넘기는 자동화에서, 모델이 자유 텍스트를 재파싱하는 대신 검증된 JSON을 그대로 전달할 수 있습니다.

FastMCP — 반환 타입 힌트로 outputSchema 자동 생성python
from pydantic import BaseModel

class LicenseFinding(BaseModel):
    component: str
    license_id: str | None       # SPDX id — 없으면 name 기반 추정
    copyleft: bool
    evidence: str

@mcp.tool()
def check_component_licenses(repository: str,
                             component: str) -> list[LicenseFinding]:
    """컴포넌트의 라이선스를 SBOM 기준으로 판정합니다."""
    ...   # 반환된 Pydantic 모델 → structuredContent + outputSchema 자동 처리

결과에 resource_link 타입을 담아 "전체 데이터는 이 리소스 URI에 있음"이라고 참조만 돌려주는 패턴도 이 버전에서 정식화됐습니다. Part 1의 원칙 3(토큰 예산)과 결합하면: 요약은 content로, 원본은 resource link로가 큰 결과의 표준 처리법입니다.

Context 객체 — 도구가 세션과 대화하는 창구

FastMCP 도구 시그니처에 ctx: Context를 추가하면 SDK가 주입해줍니다. 지금까지 흩어져 나온 기능들이 이 객체 하나로 모입니다:

  • ctx.report_progress(current, total) — 4장의 progress 통지
  • ctx.info() / ctx.debug() / ctx.error() — 4장의 프로토콜 로그 채널
  • ctx.read_resource(uri) — 자기 서버의 리소스 재사용
  • ctx.session.create_message(...) — 3장의 sampling
  • ctx.elicit(...) — 3장의 elicitation

Spring 개발자의 감각으로는, 도구 함수가 순수 함수가 아니라 세션 스코프 협력자를 주입받는 컴포넌트가 되는 지점입니다.

06 · SPRING STACK

Spring AI로 MCP 서버 만들기

기존 Spring 서비스(IVAS 백엔드 같은)에 MCP 인터페이스를 붙이는 시나리오라면 Python을 새로 끼울 이유가 없습니다. Spring AI가 MCP 서버 부트스트랩을 스타터로 제공합니다.

build.gradle
dependencies {
    // stdio 또는 Streamable HTTP(WebMVC) 서버 전송 포함
    implementation 'org.springframework.ai:spring-ai-starter-mcp-server-webmvc'
}
ImportTools.java — @Tool 기반 도구 정의java
@Service
public class ImportTools {

    private final ImportReviewService reviewService;  // 기존 서비스 재사용

    @Tool(description = """
        패키지의 반입 심사 상태를 조회합니다.
        사용 시점: 사용자가 특정 패키지의 반입 가능 여부나 심사 진행 상황을 물을 때.
        component 예시: 'lodash@4.17.21', 'org.springframework:spring-core:6.1.0'
        """)
    public ImportStatus checkImportStatus(
            @ToolParam(description = "패키지 좌표 (name@version 또는 GAV)")
            String component) {
        return reviewService.findStatus(component);
    }
}

@Bean
public ToolCallbackProvider importTools(ImportTools tools) {
    return MethodToolCallbackProvider.builder()
            .toolObjects(tools).build();

아키텍처 선택 — 서비스 내장 vs 별도 게이트웨이

MCP 서버를 기존 애플리케이션 안에 내장하면 배포가 단순하지만 릴리스 주기가 묶이고 장애 격리가 안 됩니다. 반대로 별도 프로세스로 두고 내부 API를 호출하게 하면 MCP 계층을 독립적으로 진화시킬 수 있죠. 도구 몇 개로 시작할 땐 내장, 여러 시스템(Nexus + IVAS + Jira 프록시)을 묶는 단계가 되면 MCP 게이트웨이 분리가 정석입니다 — BFF 패턴의 판단 기준과 같습니다.

07 · BUILD A CLIENT

클라이언트를 직접 만들어보기 — 에이전트 루프의 실체

호스트를 한 번 직접 만들어보면 Part 1의 6장(전체 흐름)이 손에 잡힙니다. Claude Code가 하는 일의 뼈대는 아래 50줄이 전부입니다.

host.py — 최소 호스트: MCP 클라이언트 + LLM 루프python
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client
from anthropic import Anthropic

async def run(user_query: str):
    params = StdioServerParameters(command="uv", args=["run", "server.py"])
    async with stdio_client(params) as (r, w), ClientSession(r, w) as s:
        await s.initialize()                          # ① 핸드셰이크

        tools = (await s.list_tools()).tools          # ② 카탈로그 수집
        llm_tools = [{"name": t.name,                 # ③ MCP→LLM 스키마 변환
                      "description": t.description,
                      "input_schema": t.inputSchema} for t in tools]

        llm = Anthropic()
        msgs = [{"role": "user", "content": user_query}]
        while True:                                   # ④ 에이전트 루프
            resp = llm.messages.create(model="claude-sonnet-4-6",
                       max_tokens=2048, tools=llm_tools, messages=msgs)
            if resp.stop_reason != "tool_use":
                return resp.content[0].text            # 최종 답변

            msgs.append({"role": "assistant", "content": resp.content})
            for block in resp.content:
                if block.type == "tool_use":
                    result = await s.call_tool(        # ⑤ MCP tools/call
                        block.name, arguments=block.input)
                    msgs.append({"role": "user", "content": [{
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result.content[0].text}]})  # ⑥ 복귀

이 코드가 드러내는 것들:

  • ③이 바로 "function calling과 MCP의 접합부"입니다 — MCP 도구 정의를 LLM API의 tools 파라미터로 옮기는 단순 변환이며, 이 변환이 벤더별로 다르기에 호스트가 필요한 것
  • ④의 while 루프가 "에이전트"의 실체 — 모델이 tool_use를 그만 낼 때까지 호출-실행-복귀 반복
  • 이 최소 구현엔 승인 단계가 없습니다. 프로덕션 호스트라면 ⑤ 앞에 사용자 확인, 도구별 허용 정책, 결과 크기 제한이 들어가야 합니다 — Part 1 보안 장의 방어선들이 코드상 어디에 위치하는지가 명확해지는 지점
08 · TESTING

테스트 전략 — Inspector 이후의 자동화

Inspector는 수동 검증 도구입니다. CI에 넣을 자동 테스트는 계층별로 접근합니다.

  1. L1 · 순수 로직 단위 테스트

    도구 함수의 비즈니스 로직을 MCP와 무관하게 테스트. 도구 함수가 얇은 어댑터이고 실제 로직이 별도 서비스 계층에 있다면(6장의 Spring 예처럼) 기존 테스트 관행 그대로입니다.

  2. L2 · 프로토콜 통합 테스트 — in-memory 연결

    SDK가 제공하는 인메모리 transport로 서버·클라이언트를 같은 프로세스에서 연결하면, 실제 tools/list → tools/call 왕복을 프로세스 spawn 없이 검증할 수 있습니다. 스키마 회귀(파라미터 이름 변경, 필수/옵션 변경)를 잡는 층입니다.

  3. L3 · 계약 스냅샷

    tools/list 응답 전체를 스냅샷으로 고정해두면, description이나 스키마의 의도치 않은 변경이 diff로 드러납니다. 도구 정의는 곧 모델과의 계약이므로, API 스펙 변경과 같은 무게로 리뷰해야 합니다.

  4. L4 · 모델 인 더 루프 평가 (선택)

    "이 질문 세트에 대해 모델이 올바른 도구를 올바른 인자로 선택하는가"를 주기적으로 돌리는 평가. description 수정의 효과를 측정하는 유일한 방법이지만 비용이 들므로, 도구 선택 오류가 실제로 문제가 될 때 도입합니다.

test_server.py — L2 예시python
import pytest

@pytest.mark.anyio

            mcp._mcp_server) as client:

지표이유

10 · SUMMARY

요약과 로드맵

Part 1 + Part 2를 관통하는 성장 경로.

원격 세션

단일 /mcp 엔드포인트, Mcp-Session-Id가 상태의 열쇠, SSE 스트림 + Last-Event-ID 재개. 프록시 버퍼링이 단골 장애 원인.

인증

MCP 서버 = OAuth 2.1 Resource Server. 토큰 발급은 IdP 몫, 서버는 audience 검증만. 토큰 passthrough 금지.

역방향

Sampling(지능 차용) · Elicitation(중간 질문) · Roots(경계 선언). 서버도 대화의 참여자가 될 수 있다.

운용 메시지

긴 작업엔 progress 필수, 취소는 협조적, 로그는 프로토콜 채널로, 목록은 커서 페이지네이션.

구현 선택지

Python FastMCP와 Spring AI @Tool은 대칭 구조. 기존 Spring 서비스 확장이면 Spring AI, 독립 도구면 FastMCP.

프로덕션

계층별 테스트(L1~L4), 계약 스냅샷, isError율·결과 크기 관측, 도구 정의의 버전 관리.

실습 로드맵 — 지금 스택에서 밟아볼 순서

  1. 홈랩에서 원격화 연습

    Part 1의 nexus-mcp를 streamable-http로 전환해 Proxmox LXC에 배포하고, Nginx 뒤에 두어 1장의 SSE 프록시 이슈를 직접 재현·해결해봅니다.

  2. Spring AI 대칭 구현

    같은 도구를 Spring AI @Tool로 다시 만들어 두 SDK의 대칭성을 확인 — IVAS에 붙일 때의 감각을 미리 확보합니다.

  3. 최소 호스트 작성

    7장의 50줄 호스트를 직접 돌려 에이전트 루프를 체화합니다. 승인 단계를 추가해보면 보안 설계가 코드로 이해됩니다.

  4. 테스트·관측 얹기

    L2 인메모리 테스트와 L3 스냅샷을 CI에 넣고, 도구별 지연·isError율 대시보드를 만듭니다. 여기까지 오면 팀 도입 제안이 가능한 상태입니다.
