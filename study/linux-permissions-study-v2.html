CONCEPT 01

파일 권한 기초 — owner / group / others

리눅스의 모든 파일과 디렉터리는 딱 3가지 대상에 대해 권한을 가집니다.

// ls -l 출력 구조
전체 구조 d rwx owner rwx group r-- others labrador appgrp except_list/
d — 파일 타입 d = directory  |  - = 일반파일  |  l = 심볼릭링크
대상설명이번 사례
owner 파일 소유자 본인 root (txt 파일 소유자)
group 파일의 소유 그룹에 속한 사용자들 root 그룹 (labrador 미포함)
others owner도 group도 아닌 나머지 모든 사용자 labrador 해당 → 읽기만
Qothers 권한이라는 게 뭐야?
A 파일의 owner도 아니고 group 멤버도 아닌 나머지 모든 사람에게 적용되는 권한입니다. 이번 사례에서 txt 파일이 root:root 소유라서 labrador는 others로 분류됐고, others 권한이 r-- (읽기만)이어서 쓰기가 불가했습니다.
Qx 와 - 차이가 뭐야?
A 파일: x = 실행 가능 (스크립트, 바이너리), - = 실행 불가
디렉터리: x = 디렉터리 안으로 cd 진입 가능, - = 진입 불가

디렉터리에서 r만 있으면 ls 목록은 보이지만 cd 불가. x만 있으면 cd는 되지만 ls 불가. r+x 둘 다 있어야 정상 사용 가능합니다.
CONCEPT 02

권한 비트 전체 구조 — 12비트

기본 9비트(owner/group/others) 앞에 특수 비트 3개가 붙어 총 12비트가 됩니다. 단, 특수 비트는 별도 자리가 없고 기존 x 자리를 빌려서 s, t 로 표시합니다.

// 12비트 전체 구조
비트 구성 d 타입 | s s t 특수 | rwx owner | rws group+setgid | r-x others
setuid (u+s) — 실행 파일: 실행 중에 소유자 권한으로 동작. 예) passwd 명령어
setgid (g+s) — 디렉터리: 하위 파일 그룹 자동 상속 ← 이번 사례
sticky (o+t) — 디렉터리: 파일 소유자만 삭제 가능. 예) /tmp
Q특수비트는 sst인데 왜 맨앞에 d가 붙어?
A d는 특수비트가 아니라 파일 타입을 나타내는 별도 자리입니다. d = directory, - = 일반파일, l = 심볼릭링크 구조는 [타입 1자리] + [owner 3자리] + [group 3자리] + [others 3자리] = 총 10자리가 ls에 표시됩니다. 특수비트는 이 10자리 안에서 x 자리를 빌려 s/t로 표시됩니다.
CONCEPT 03

setgid — 그룹 상속 비트 상세

디렉터리에 setgid가 설정되면 그 안에 새로 생성되는 파일의 그룹이 만든 사람의 GID가 아니라 디렉터리의 그룹으로 자동 상속됩니다.

// setgid 유무에 따른 파일 생성 결과
setgid OFF root가 파일 생성 → root:root ← labrador는 others → 쓰기 불가
setgid ON root가 파일 생성 → root:appgrp ← 디렉터리 그룹 상속 → labrador 쓰기 가능
// ls 출력에서 s 표시 위치와 의미
소문자 s drwxrwsr-x = setgid ON + group execute ON → 정상
대문자 S drwxrwSr-x = setgid ON + group execute OFF → 실무에서 실수 신호
Q대문자 S 되면 뭐가 달라?
A setgid 기능 자체는 똑같이 작동합니다. 차이는 group execute(x) 유무뿐입니다. 대문자 S면 appgrp 멤버가 디렉터리 안으로 cd 진입 자체가 불가합니다. setgid는 작동하지만 진입을 못 하니 의미가 없습니다. 실무에서 S가 보이면 x를 실수로 뺀 것일 가능성이 높습니다.
Q의미가 없으면 왜 S가 있어? 그냥 g+rw- 하면 되는 거 아냐?
A 맞는 지적입니다. S는 설정 순서가 달랐을 때 생기는 흔적입니다. setgid를 먼저 걸고(chmod g+s) 나중에 x만 따로 제거(chmod g-x)하면 생깁니다. 리눅스가 setgid 비트와 x 비트를 각각 독립적으로 관리하기 때문입니다. 처음부터 g+rw만 주고 setgid를 안 걸면 S 자체가 생기지 않습니다.
Qsetgid를 끄면 어떻게 돼?
A 그룹 자동 상속이 사라집니다. 이후 root가 파일을 만들면 다시 root:root가 됩니다. 단, 이미 만들어진 파일에는 영향 없습니다. setgid는 파일 생성 시점에만 작동하기 때문입니다.
BASHsetgid 설정 명령어
# setgid 설정 (g+rwxs: group에 rwx + setgid) sudo chmod g+rwxs /path/to/except_list # 8진수 표현: 2=setgid, 7=rwx owner, 7=rwx group, 5=r-x others sudo chmod 2775 /path/to/except_list # 확인 ls -ld /path/to/except_list drwxrwsr-x 2 labrador appgrp 4096 May 28 17:00 except_list # ↑ 's' (소문자) = setgid ON + group x ON
CONCEPT 04

umask — 권한 자동 차감 마스크

umask는 파일 생성 시 권한을 자동으로 빼는 마스크입니다. 리눅스에서 파일을 만드는 모든 프로세스가 umask를 적용합니다. 도커 컨테이너도 예외가 없습니다.

// umask 022 계산 예시
기본 권한 666 (rw-rw-rw-) ← 파일 생성 시 기본값
umask 022 (----w--w-) ← group w, others w 제거
실제 권한 644 (rw-r--r--) ← group 쓰기 제거됨
umask 022 자리별 의미: 0=owner 아무것도 안 뺌  |  2=group에서 w 제거  |  2=others에서 w 제거
Qumask는 누가 설정해?
A 여러 단계에서 설정되며 하위가 상위를 덮어씁니다.
/etc/profile (시스템 전체 기본값) → ~/.bashrc (사용자별) → Dockerfile / 컨테이너 런타임 (컨테이너)
022가 기본값인 이유는 보안상 group/others 쓰기를 막는 게 일반적인 관행이기 때문입니다.
Q도커가 파일을 쓸 때 늘 umask 적용해서 생성한다는 거지?
A 네 맞습니다. 도커뿐 아니라 리눅스에서 파일을 생성하는 모든 프로세스가 umask를 적용합니다. 이번 사례는 두 가지 문제가 겹쳤습니다.
① 컨테이너가 root로 실행 → 파일 소유가 root:root
② umask 022 적용 → group w 제거
그래서 setgid 하나만으론 부족하고 default ACL까지 같이 써야 했습니다.
BASHumask 확인
umask 0022 # 숫자로 출력 umask -S u=rwx,g=rx,o=rx # 문자로 출력
⚠
setgid만으로 부족한 이유
setgid는 그룹 이름(appgrp)을 맞춰주지만, 파일 권한(rwx)은 umask가 결정합니다. umask 022라면 group w가 제거되어 그룹이 맞아도 쓰기가 불가합니다. default ACL이 umask를 우회하여 group:rwx를 강제 보장합니다.
CONCEPT 05

ACL — Access Control List

QACL은 무슨 목적으로 만들어진 명령어야?
A 기본 Linux 권한(owner/group/others 3단계)이 너무 단순해서 생긴 한계를 해결하려고 만들어졌습니다. 예를 들어 특정 사람 한 명에게만 읽기 권한을 주고 싶어도, 기본 권한으로는 방법이 없습니다. 그 사람을 group에 넣으면 group 전체와 동일해지고, others를 열면 모든 사람에게 열립니다. ACL은 누구에게든 개별적으로 권한을 설정할 수 있습니다.
QACL은 리눅스에 있는 기본 명령어야?
A ACL 기능 자체는 커널에 내장되어 있습니다. 다만 setfacl/getfacl 명령어는 acl 패키지 설치 필요합니다. ext4, xfs 파일시스템은 ACL을 기본 지원하며, 실무 서버 환경에서는 대부분 이미 설치되어 있습니다.
구분기본 Linux 권한ACL
대상 지정 owner, group, others 3가지만 임의의 user, group 여러 개 가능
유연성 그룹 변경 필요 파일 소유 변경 없이 권한 추가
신규 파일 상속 상속 없음 default ACL로 자동 상속
확인 명령어 ls -l getfacl
표시 -rwxrwxr-x -rwxrwxr-x+ (끝에 + 표시)

# default ACL 설정 (-d: default, -m: modify) # 이후 생성되는 모든 파일에 group rwx 자동 부여 sudo setfacl -d -m g::rwx /path/to/except_list # ACL 확인 getfacl /path/to/except_list # file: except_list # owner: labrador # group: appgrp # flags: -s- ← setgid 활성화됨 user::rwx group::rwx other::r-x default:user::rwx default:group::rwx ← 신규 파일에도 group rwx 자동 적용 default:other::r-x # ACL 있는 파일은 ls -l 끝에 '+' 표시 -rw-rw-r--+ 1 root appgrp 1234 May 28 excepList_20260528.txt
CONCEPT 06

Docker 컨테이너와 파일 권한

Qlabrador 유저가 docker compose up으로 실행했는데 왜 유저가 root야?
A 컨테이너를 실행하는 사람과 컨테이너 안에서 동작하는 유저는 별개입니다. labrador가 docker compose up을 실행하면 도커 데몬(root 권한)이 컨테이너를 시작하고, 컨테이너 내부는 독립된 환경입니다. Dockerfile에 USER 지정이 없으면 기본으로 root로 실행됩니다.
// 컨테이너 실행 흐름
호스트: labrador 가 docker compose up → 도커 데몬(root)이 컨테이너 시작
컨테이너: Dockerfile에 USER 없음 → 컨테이너 내부 프로세스 = root
파일 생성: root가 파일 생성 + umask 022 → root:root, group w 없음
ℹ
비유: labrador가 가게 문을 열었다고(docker compose up) 가게 안 직원이 labrador인 건 아닙니다. 직원이 누군지는 고용 계약서(Dockerfile의 USER 지시어)에 달려있습니다.
ROOT CAUSE

원인 분석 — 두 가지가 겹침

// 문제 상황 권한 분석
디렉터리 rwx owner(labrador) rwx group(appgrp) r-x others
txt 파일 ❌ rw- owner(root) r-- group(root) r-- others ← labrador는 others → 읽기만
⚠
원인 1: 컨테이너가 root로 실행 → 파일 소유가 root:root (setgid 없어서 그룹 상속 안 됨)
원인 2: umask 022 → group w 제거
두 원인이 겹쳐서 labrador는 others로 분류되어 읽기만 가능한 상태.
ACTION

임시 조치 절차

labrador 계정이 appgrp 멤버인지 확인

이 전제가 충족되어야 그룹 권한이 적용됩니다.

id labrador | grep -o appgrp # 출력에 'appgrp' 이 있어야 함

디렉터리에 setgid + default ACL 부여

이후 컨테이너(root)가 생성하는 신규 파일도 자동으로 group=appgrp, g+rw가 됩니다.

sudo chmod g+rwxs /path/to/except_list sudo setfacl -d -m g::rwx /path/to/except_list

기존 root:root 파일 일괄 보정

이미 쌓인 파일들은 setgid/ACL 설정 이전 생성이므로 별도로 정리합니다.

sudo chgrp -R appgrp /path/to/except_list sudo chmod g+rw /path/to/except_list/*.txt
VERIFY

3단계 검증 — 동환님 확인 완료 ✅

A. AccessDenied 중단 확인
grep AccessDenied /data/log/downloader/$(date +%Y-%m-%d)_downloader.log | tail -1
마지막 에러 시각이 조치 시점 이전이면 성공
B. 신규 파일 그룹 확인
ls -la /path/to/except_list | head
새로 떨어진 파일이 root:appgrp이면 정상
C. ACL 규칙 확인
getfacl /path/to/except_list | head
"default:group::rwx" 줄이 보이면 정상

CHEATSHEET

명령어 치트시트

BASH파일 권한 확인
ls -la <dir> # 권한 + 소유자 확인 stat -c '%U:%G' <file> # user:group 출력 id <username> # 사용자의 uid/gid/groups 확인
BASHsetgid
chmod g+s <dir> # setgid 설정 chmod g-s <dir> # setgid 제거 chmod 2775 <dir> # 8진수 (2=setgid) # 's' = setgid ON + group x ON # 'S' = setgid ON + group x OFF (실수 신호)
BASHACL
getfacl <file> # ACL 조회 setfacl -m u:username:rw <file> # 특정 사용자에게 ACL 추가 setfacl -m g:groupname:rw <file> # 특정 그룹에게 ACL 추가 setfacl -d -m g:appgrp:rwx <dir> # default ACL (신규 파일 자동 상속) setfacl -x u:username <file> # 특정 항목 제거 setfacl -b <file> # 모든 ACL 제거 setfacl -R -m g:appgrp:rw <dir> # 재귀 적용
BASHumask
umask # 현재 umask 확인 (숫자) umask -S # 현재 umask 확인 (문자) umask 002 # 임시 변경 (group w 허용)
