프레임워크가 대신 쓰는 패턴, 그리고 내가 직접 짜는 패턴

Spring을 쓰면 이미 절반의 디자인 패턴은 컨테이너가 알아서 적용하고 있다. 나머지 절반은 애플리케이션 코드에서 직접 설계해야 하는 것들이다. 이 둘을 갈라서 보면, "패턴을 안다"가 아니라 "언제 왜 쓰는지 안다"로 넘어갈 수 있다.

알게 모르게 — 프레임워크가 적용

Spring 내부 구현이거나, 애노테이션 하나로 컨테이너가 대신 엮어준다. 원리를 알면 함정(self-invocation 등)을 피한다.

직접 설계 — 내 코드의 판단

인터페이스를 뽑고 구현체를 나누는 건 내 몫이다. 면접에서 "설계할 줄 안다"를 보여주는 지점.

Framework

싱글톤Singleton

Bean의 기본 스코프. 컨테이너가 타입당 인스턴스를 하나만 만들어 모든 주입 지점이 같은 객체를 공유한다. 그래서 Bean은 상태를 갖지 않게(stateless) 설계해야 한다.

Spring 어디에 @Service, @Component, @Repository 모두 기본이 싱글톤. ApplicationContext가 인스턴스 레지스트리 역할.
함정
싱글톤 Bean에 인스턴스 필드로 상태를 두면 멀티스레드에서 공유돼 버그. 요청 상태는 메서드 파라미터나 @Scope("prototype")로.
SbomParser.java 
// 컨테이너가 단 하나만 생성 → 모든 주입 지점이 동일 인스턴스
@Service
public class SbomParser {

    // ⚠ 요청별 상태를 필드로 두지 말 것 (공유됨)
    public Sbom parse(byte[] raw) {
        // stateless: 파라미터로만 상태를 다룸
        return CycloneDx.read(raw);
    }
}

// 두 곳에 주입해도 == 로 같은 객체
@Autowired SbomParser a;
@Autowired SbomParser b;   // a == b
Framework

프록시Proxy

Spring AOP의 심장. 원본 Bean을 감싼 프록시 객체가 호출을 가로채 트랜잭션·캐시·비동기 같은 부가 로직을 앞뒤로 끼운다. 애노테이션이 곧 "여기 프록시 걸어라"는 신호.

Spring 어디에 @Transactional, @Cacheable, @Async, @Retryable. 인터페이스 있으면 JDK 동적 프록시, 없으면 CGLIB 서브클래싱.
함정
같은 클래스 안에서 자기 메서드를 부르면(self-invocation) 프록시를 안 거쳐 @Transactional이 무시된다. 이 함정을 설명하면 원리를 아는 걸로 인정받는다.
NexusApiService.java 
@Service
public class NexusApiService {

    // 프록시가 캐시 조회 → 없으면 원본 실행 → 결과 저장
    @Cacheable("assets")
    @Transactional(readOnly = true)
    public Asset findAsset(String id) {
        return repo.fetch(id);
    }

    public void refresh(String id) {
        // ⚠ self-invocation → 프록시 우회, 캐시 안 탐!
        findAsset(id);
    }
}
Framework

템플릿 메서드Template Method

골격 흐름은 상위가 고정하고, 변하는 단계만 하위/콜백에 위임한다. 이름부터 Template인 Spring 클래스들이 정확히 이 패턴 — 연결·예외처리·정리는 프레임워크가, 쿼리·매핑만 내가.

Spring 어디에 JdbcTemplate, RestTemplate, TransactionTemplate, RedisTemplate. 리소스 열고 닫는 반복을 프레임워크가 삼킨다.
포인트
"보일러플레이트(연결/close/예외)를 프레임워크가 고정하고 나는 RowMapper 콜백만 넘긴다"고 말하면 패턴 이해가 드러난다.
AssetDao.java 
// 연결·PreparedStatement·close·예외변환 = JdbcTemplate이 고정
// 변하는 부분(SQL + row 매핑)만 콜백으로 주입
List<Asset> assets = jdbc.query(
    "SELECT id, name FROM asset WHERE repo = ?",
    (rs, rowNum) -> new Asset(          // ← 내 몫
        rs.getString("id"),
        rs.getString("name")
    ),
    repoName
);
Deep-dive

왜 인터페이스가 아니라 추상 클래스인가

템플릿 메서드 패턴은 인터페이스가 아니라 추상 클래스를 쓴다. 추상 클래스에 알고리즘 흐름을 고정하는 템플릿 메서드(보통 final)를 두고, 그 안에서 호출하는 세부 단계만 추상 메서드 또는 기본 구현이 있는 hook 메서드로 선언한다. 하위 클래스는 그 추상 클래스를 extends해서 세부 단계만 오버라이드한다. 인터페이스는 원칙적으로 구현 코드를 가질 수 없어서, "공통 로직은 부모가 갖고 가변 부분만 자식이 채운다"는 이 패턴의 핵심에는 상속 기반 재사용이 자연스러운 추상 클래스 쪽이 맞다.

상속 방식implements, 다중 구현 가능extends, 단일 상속만
필드(상태)상수만 가능일반 인스턴스 필드 보유 가능
메서드 구현원칙적으로 없음 (8+ default로 일부 가능)구체 + 추상 메서드 혼합
생성자없음있음
관계 표현"~할 수 있다" (Comparable, Runnable)"~의 일종이다" (Animal → Dog)

DataProcessor.java 
abstract class DataProcessor {

    // 템플릿 메서드: 흐름은 고정, final이라 오버라이드 불가
    public final void process() {
        readData();
        processData();            // 추상 — 자식이 반드시 구현
        if (needsValidation()) {  // hook — 선택적 오버라이드
            validate();
        }
        saveData();
    }

    private void readData() { ... }
    protected abstract void processData();
    protected boolean needsValidation() { return true; } // 기본값 제공
    private void validate() { ... }
    private void saveData() { ... }
}

class JsonProcessor extends DataProcessor {
    @Override protected void processData() { ... }

    @Override
    protected boolean needsValidation() { return false; } // JSON은 검증 스킵
}

JdbcTemplate 내부 구조 — 인터페이스 + 추상 클래스 조합

JdbcTemplate이 이 둘을 실무에서 같이 쓰는 대표 예다. JdbcAccessor(추상 클래스)를 상속해 DataSource·예외 변환기 같은 공통 인프라를 재사용하고, JdbcOperations(인터페이스)를 구현해 query()·update() 같은 계약을 노출한다.

JdbcTemplate (simplified) 
public abstract class JdbcAccessor {
    private DataSource dataSource;
    private SQLExceptionTranslator exceptionTranslator;

    // Bean 초기화 시 자동 호출 — 필수 설정 검증
    public void afterPropertiesSet() {
        if (getDataSource() == null)
            throw new IllegalArgumentException("dataSource is required");
    }
}

public interface JdbcOperations {
    <T> T queryForObject(String sql, RowMapper<T> mapper);  // 계약만
    int update(String sql, Object... args);
}

public class JdbcTemplate extends JdbcAccessor          // 공통 인프라 상속
                                implements JdbcOperations {  // 계약 구현
    @Override
    public <T> T queryForObject(String sql, RowMapper<T> mapper) {
        try {
            // getDataSource() — 부모가 관리하던 걸 그대로 사용
            Connection con = DataSourceUtils.getConnection(obtainDataSource());
            ...
        } catch (SQLException ex) {
            throw getExceptionTranslator().translate("Query", sql, ex);  // 부모가 세팅한 translator
        }
    }
}

팩토리 메서드Factory Method

객체 생성 책임을 별도 주체에 위임한다. Spring 컨테이너 자체가 거대한 팩토리 — getBean()이 팩토리 메서드다. @Bean 메서드도 "이 객체는 이렇게 만들어라"는 팩토리.

Spring 어디에 BeanFactory, ApplicationContext#getBean(), @Bean 메서드, FactoryBean<T> 인터페이스.
연결
직접 설계할 때도 유용: 포맷(CycloneDX/SPDX)에 따라 구현체를 골라 만드는 팩토리로 new 분기를 한곳에 모은다.

@Configuration
public class AppConfig {

    // @Bean 메서드 = "이 타입은 이렇게 생성하라"는 팩토리
    @Bean
    public Validator validator(Props p) {
        return new StrictValidator(p.threshold());

}

// 컨테이너(팩토리)에서 꺼내 쓰기

책임 연쇄Chain of Responsibility

요청을 처리기들의 사슬에 흘려보내고, 각 노드가 처리하거나 다음으로 넘긴다. Servlet Filter와 Spring Security의 필터 체인이 교과서적 구현.

Spring 어디에 javax.servlet.Filter 체인, Spring Security FilterChainProxy, HandlerInterceptor.
포인트
chain.doFilter()를 부르면 다음으로 넘어가고, 안 부르면 거기서 요청이 끊긴다 — 인증 실패 차단이 이 원리.
ApiKeyFilter.java 
public class ApiKeyFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req,
                         ServletResponse res,
                         FilterChain chain) throws IOException, ServletException {

        if (!hasValidKey(req)) {
            reject(res);
            return;          // 사슬 끊음 → 다음 필터/컨트롤러 도달 못 함
        }
        chain.doFilter(req, res); // 다음 처리기로 위임
    }
}

전략Strategy

교체 가능한 알고리즘을 인터페이스로 뽑고, 조건별로 구현체를 나눈다. if-else로 쌓이던 분기를 클래스로 분리 — 새 규칙이 생겨도 기존 코드는 안 건드린다(OCP). Spring에선 구현체를 Map으로 주입받아 키로 고른다.

실무 적용 Nexus 자산 중복 제거 로직을 exceptList 기반 / 해시 기반으로 나눠 전략화. 규칙 추가 = 구현체 1개 추가.
면접
"조건마다 다르던 dedup을 전략 인터페이스로 뽑아 Map 주입으로 선택, OCP 지킴." 꼬리질문 → "상속(Template Method) 대신 조합을 택한 이유"까지 준비.
DeduplicationStrategy.java 
// 1. "중복 제거"라는 행위를 인터페이스로 추상화
public interface DeduplicationStrategy {
    List<Asset> dedupe(List<Asset> assets);
}

// 2. 방식별 구현체 (Bean 이름 = 선택 키)
@Component("exceptList")
class ExceptListDedup implements DeduplicationStrategy { ... }

@Component("hash")
class HashDedup implements DeduplicationStrategy { ... }

// 3. 사용처는 Map으로 주입받아 키로 선택
@Service
class AssetService {
    private final Map<String, DeduplicationStrategy> strategies;

    AssetService(Map<String, DeduplicationStrategy> s) {
        this.strategies = s;   // Spring이 Bean이름→구현체 Map 자동 구성
    }
    List<Asset> process(String type, List<Asset> a) {
        return strategies.get(type).dedupe(a);
    }
}

템플릿 메서드Template Method · 내 코드

여러 처리기가 흐름(검증→처리→알림)은 같고 중간만 다를 때, 공통 흐름을 상위 final 메서드로 고정하고 변하는 단계만 추상 메서드로 뺀다. 순서를 실수로 바꾸는 걸 컴파일 단계에서 막는다.

실무 적용 import 프로세서가 여러 종류인데 검증 → 처리 → 결과알림 순서는 동일, 실제 import 방식만 상이.
면접
"흐름 순서를 final로 잠가 실수 방지." 단, 유연함이 더 필요하면 Strategy로 조합하는 게 낫다는 트레이드오프도 알아두기.

public abstract class AbstractImportProcessor {

        notifyResult(req);
    }

    protected abstract void doImport(ImportRequest req);

    private void validate(ImportRequest req) { /* 공통 */ }
    private void notifyResult(ImportRequest req) { /* 공통 */ }
}

class DockerImport extends AbstractImportProcessor {

옵저버Observer

이벤트를 발행하면 관심 있는 구독자들이 각자 반응한다. 발행자는 구독자를 모른다(느슨한 결합). Spring이 ApplicationEventPublisher를 제공하지만, 무슨 이벤트를 언제 쏘고 누가 들을지는 내 설계.

실무 적용 import 완료 시 ImportCompletedEvent 발행 → 대시보드 갱신·알림·통계 배치가 각자 구독. 서비스 간 직접 호출 제거.
면접
"import 서비스가 대시보드를 직접 부르면 결합↑. 이벤트로 분리해 관심사 분리." 동기/비동기(@Async) 처리 차이도 짚기.

// 발행 — 누가 듣는지 몰라도 됨

class ImportService {

// 구독 — 관심 있는 쪽이 각자 반응

빌더Builder

인자 많고 선택 필드가 뒤섞인 객체를, 이름 붙은 단계로 안전하게 조립한다. 텔레스코핑 생성자의 순서 실수·가독성 문제를 없애고 불변 객체를 만든다. Lombok @Builder로 흔히 쓰지만, 왜 필요한지가 핵심.

실무 적용 Sbom처럼 format·version·components·optional 필드가 많은 도메인 객체 생성. UriComponentsBuilder도 같은 패턴.
면접

어댑터Adapter

호환되지 않는 두 인터페이스를 이어 붙인다. 외부 시스템의 응답 모양을 내 도메인 모델로 변환하는 계층이 대표적 — 외부 스펙 변화가 도메인까지 번지는 걸 막는 방벽.

실무 적용 Nexus REST 응답(NexusAssetResponse)을 내부 Asset 도메인으로 변환. 외부 API 바뀌어도 어댑터만 수정.
면접
"외부 응답 스펙을 도메인에 직접 물리면 결합↑. 어댑터로 변환 지점을 한곳에 격리." 안티코럽션 레이어(ACL) 개념과 연결하면 강함.
NexusAssetAdapter.java 
// 외부(Nexus) 표현 → 내부 도메인 표현
@Component
public class NexusAssetAdapter {

    public Asset toDomain(NexusAssetResponse res) {
        return Asset.builder()
            .id(res.getId())
            .name(res.getPath())              // 필드명 매핑
            .repo(res.getRepository())
            .sha256(res.getChecksum().sha256()) // 구조 평탄화
            .build();
    }
}

데코레이터Decorator

원본과 같은 인터페이스를 유지한 채 감싸서 기능을 덧입힌다. 상속 없이 로깅·검증·재시도 같은 부가 기능을 층층이 쌓을 수 있다. BufferedReader가 스트림을 감싸는 게 같은 원리.

실무 적용 LicenseValidator를 감싼 LoggingValidator로 검증 전후 로그 추가 — 원본 검증 로직은 그대로.
면접
"기능 추가하려고 상속 트리 늘리는 대신 감싸서 합성." 프록시와 차이(데코는 기능 추가 의도, 프록시는 접근 제어)를 구분하면 좋음.
LoggingValidator.java 
// 같은 인터페이스를 구현하면서 원본을 감쌈
public class LoggingValidator implements LicenseValidator {

    private final LicenseValidator delegate;

    public LoggingValidator(LicenseValidator delegate) {
        this.delegate = delegate;
    }

    @Override
    public Result validate(Sbom sbom) {
        log.info("validating {}", sbom.serialNumber());
        Result r = delegate.validate(sbom);  // 원본 위임
        log.info("result: {}", r.status());
        return r;                            // 부가기능 + 원본
    }
}

01

문제 상황

02

대안 검토

고려한 선택지들. "분기 유지 vs 전략 분리 vs 상속."

03

선택 이유

왜 이걸. "규칙 추가가 잦아 OCP가 중요 → Strategy."

04

트레이드오프

대가는. "구현체·Bean이 늘어 관리 포인트 증가."

모범 답변 · Strategy를 메인으로 Nexus 자산 중복 제거 로직이 조건마다 달라서 if-else로 쌓이던 걸 DeduplicationStrategy 인터페이스로 분리했습니다. exceptList 기반 처리와 해시 기반을 다른 전략으로 두고 Map으로 주입받아 타입별로 선택하게 했어요. 새 규칙이 생겨도 기존 코드는 안 건드리고 구현체만 추가하면 돼서 OCP를 지킬 수 있었습니다. 빌더는 Sbom처럼 선택 필드가 많은 도메인 객체를 불변으로 안전하게 만들려고 곁들여 썼습니다.
