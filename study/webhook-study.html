Technical Study

Webhook

이벤트 기반 HTTP 콜백 메커니즘의 동작 원리와 구현 패턴

개념 동작 흐름 vs Polling Payload 보안 재시도 구현 예제 실사용 사례
01 / Concept

Webhook이란?

Webhook은 특정 이벤트가 발생했을 때 외부 URL로 HTTP POST 요청을 자동으로 전송하는 메커니즘입니다. "역방향 API(Reverse API)" 또는 "HTTP Push"라고도 불립니다.

기존 API는 클라이언트가 서버에 요청(pull)하지만, Webhook은 서버가 클라이언트에 능동적으로 통보(push)합니다.

📌 핵심 특성
  • 이벤트 발생 시 즉각 HTTP 요청 발송
  • 수신 측이 미리 URL(Endpoint)을 등록
  • 대부분 JSON/XML body를 포함한 POST 요청
  • 비동기 방식으로 동작
🔧 주요 활용 분야
  • 결제 완료 알림 (Stripe, Toss)
  • CI/CD 파이프라인 트리거 (GitHub)
  • 메신저 봇 이벤트 수신
  • 외부 시스템 간 데이터 동기화

단계별 설명

단계주체설명
1. 등록 Consumer → Provider 수신할 이벤트 종류와 Callback URL을 Provider에 등록 (대시보드 or API)
2. 이벤트 발생 Provider 내부 DB 변경, 사용자 행동 등 구독한 이벤트 발생
3. 요청 전송 Provider → Consumer 등록된 URL로 HTTP POST + Payload(JSON) 전송
4. 처리 & 응답 Consumer 수신 후 비즈니스 로직 처리, 5초 내 2xx 응답 반환 권장
5. 재시도 Provider 2xx 미수신 시 지수 백오프(Exponential Backoff)로 재시도
⚡ 핵심 원칙: Webhook 수신 엔드포인트는 빠르게 응답(200 OK)하고, 무거운 처리는 비동기 큐에 위임해야 합니다. 처리 시간이 길면 Provider가 타임아웃으로 실패 처리합니다.
03 / Comparison

Webhook vs Polling

항목 Webhook (Push) Polling (Pull)
트리거 이벤트 발생 시 즉시 일정 주기 (e.g. 30초마다)
실시간성 높음 수 초 내 수신 낮음 주기 지연 발생
서버 부하 낮음 이벤트 시에만 요청 높음 불필요 요청 다수
구현 복잡도 수신 서버 필요, 보안 처리 요구 간단, 별도 인프라 불필요
네트워크 비용 적음 많음 (빈 응답 포함)
적합한 상황 이벤트 빈도 낮고 실시간성 중요 이벤트 빈도 높거나 수신 서버 구성 불가
04 / Payload

Payload 구조

Webhook Payload는 이벤트 메타정보와 실제 데이터를 포함한 JSON입니다. 표준 규격은 없지만 일반적으로 아래 필드를 포함합니다.

JSON · Webhook Payload 예시 
{
  "id":         "evt_1Nw3kBJ2eZvKYlo2C5xRlBo",      // 이벤트 고유 ID (멱등성 처리용)
  "type":       "payment.completed",            // 이벤트 타입
  "created_at": 1718000000,                    // Unix timestamp (UTC)
  "api_version": "2024-01",
  "data": {
    "object": "payment",
    "amount": 50000,
    "currency": "KRW",
    "status": "succeeded",
    "customer_id": "cus_abc123"
  }
}

HTTP 요청 헤더

HTTP Headers 
POST /webhook/payment HTTP/1.1
Host: your-server.com
Content-Type: application/json
X-Webhook-Signature: sha256=3b4c5d6e...     # HMAC 서명 (보안)
X-Webhook-ID: evt_1Nw3kBJ2eZvKYlo2C5xRlBo  # 이벤트 ID
X-Webhook-Timestamp: 1718000000              # 전송 시각 (리플레이 방어)
User-Agent: ProviderWebhook/1.0
05 / Security

보안 처리

HMAC 서명 검증

Provider는 공유 Secret Key를 사용해 Payload를 HMAC-SHA256으로 서명하고 헤더에 포함합니다. Consumer는 이를 재계산해 비교합니다.

Python · HMAC 서명 검증 
import hmac, hashlib

def verify_webhook(payload_bytes, signature_header, secret):
    # 헤더에서 sha256= 제거
    expected = hmac.new(
        secret.encode(),
        payload_bytes,
        hashlib.sha256
    ).hexdigest()

    received = signature_header.removeprefix("sha256=")

    # 타이밍 공격 방지: compare_digest 사용
    if not hmac.compare_digest(expected, received):
        raise ValueError("Invalid webhook signature")

    return True
⚠ 주의: == 연산자 대신 hmac.compare_digest()를 사용하세요. 일반 문자열 비교는 타이밍 사이드채널 공격에 취약합니다.

타임스탬프 검증 (Replay Attack 방어)

Python · Replay Attack 방어 
import time

def check_timestamp(timestamp_header, tolerance_seconds=300):
    ts = int(timestamp_header)
    now = int(time.time())

    if abs(now - ts) > tolerance_seconds:  # 5분 초과 시 거부
        raise ValueError("Webhook timestamp too old")

# 서명 생성 시 timestamp도 포함하는 패턴 (Stripe 방식)
message = f"{timestamp}.{payload_body}"
signature = hmac.new(secret, message.encode(), hashlib.sha256).hexdigest()

06 / Retry

재시도 & 멱등성

Provider는 2xx 응답을 받지 못하면 지수 백오프(Exponential Backoff) 방식으로 재시도합니다. 따라서 Consumer는 동일 이벤트를 여러 번 받을 수 있습니다.

재시도 횟수대기 시간 (예시)누적 경과
1차즉시0초
2차5초5초
3차30초35초
4차5분~6분
5차30분~36분
이후최대 수 시간최대 72시간

멱등성 처리 패턴

Python (FastAPI) · 멱등성 처리 
from fastapi import Request, HTTPException
import redis

r = redis.Redis(host='localhost')

@app.post("/webhook/payment")
async def handle_webhook(request: Request):
    event_id = request.headers.get("X-Webhook-ID")

    # 이미 처리한 이벤트인지 확인 (TTL 72시간)
    if r.exists(f"webhook:processed:{event_id}"):
        return {"status": "already_processed"}

    payload = await request.json()

    # ✅ 빠르게 큐에 위임 (타임아웃 방지)
    background_tasks.add_task(process_payment, payload)

    # 처리 완료 마킹 (72시간 유효)
    r.setex(f"webhook:processed:{event_id}", 259200, "1")

    return {"status": "accepted"}  # 즉시 200 반환
💡 Exactly-Once 처리: 동일한 event_id가 들어오면 중복 처리 없이 200 OK만 반환해야 합니다. DB의 UNIQUE 제약이나 Redis SET NX 패턴을 활용하세요.
07 / Implementation

전체 구현 예제

Python (FastAPI) · 프로덕션급 Webhook 수신 서버 
from fastapi import FastAPI, Request, HTTPException, BackgroundTasks
from pydantic import BaseModel
import hmac, hashlib, time, logging

app = FastAPI()
WEBHOOK_SECRET = "your_secret_key"

def verify_signature(body: bytes, sig: str, ts: str) -> bool:
    # Stripe 방식: timestamp.body 에 서명
    message = f"{ts}." + body.decode()
    expected = hmac.new(
        WEBHOOK_SECRET.encode(), message.encode(), hashlib.sha256
    ).hexdigest()
    if not hmac.compare_digest(f"sha256={expected}", sig):
        raise HTTPException(401, "Invalid signature")
    if abs(int(ts) - int(time.time())) > 300:
        raise HTTPException(400, "Timestamp too old")

async def process_event(event: dict):
    # 실제 비즈니스 로직 (백그라운드 실행)
    event_type = event.get("type")
    logging.info(f"Processing event: {event_type}")
    # ... 처리 로직

@app.post("/webhook")
async def webhook_endpoint(
    request: Request,
    background_tasks: BackgroundTasks
):
    body = await request.body()      # raw bytes 로 읽어야 서명 검증 가능
    sig  = request.headers.get("X-Webhook-Signature", "")
    ts   = request.headers.get("X-Webhook-Timestamp", "0")

    verify_signature(body, sig, ts)    # 검증 실패 시 자동으로 예외 발생

    event = await request.json()
    background_tasks.add_task(process_event, event)

    return {"status": "ok"}            # 즉시 200 반환

Dead Letter Queue 패턴

최대 재시도 횟수 초과 시 이벤트를 Dead Letter Queue(DLQ)에 저장하여 나중에 수동 재처리하거나 알림을 받는 패턴입니다.

Architecture · DLQ Pattern 
Webhook Provider
    │
    ▼ (실패 시 재시도 × N)
[Main Queue] ──실패──→ [Dead Letter Queue]
    │                        │
    ▼ 정상 처리              ▼ 알림 / 수동 처리
[Application]          [Slack Alert / Dashboard]
💡 모니터링 포인트: Webhook 수신 성공률, 평균 응답 시간, 재시도 발생 횟수, DLQ 적재량을 대시보드로 관리하면 장애를 조기에 탐지할 수 있습니다.
