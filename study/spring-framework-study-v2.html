01 — TOPOLOGY

전체 위상 구조: 한 장의 지도

스프링의 구성요소들은 같은 레벨이 아니다. 아래에서 위로: 실행 환경 → 코어 → 메커니즘 → 모듈 순으로 위상이 갈린다.

③ 모듈
WebMVC · Security · Spring Data/Tx
코어를 사용하는 층. 각 모듈의 구성요소(Controller, 설정 객체 등)는 전부 Bean으로 등록되어 ①의 지배를 받는다. Security의 FilterChain만 예외적으로 DispatcherServlet 앞단의 서블릿 필터 레벨에서 동작.
② 메커니즘
DI · AOP(프록시)
"어디에 있는 것"이 아니라 "어떻게 작동하는 것". 특정 층에 속하지 않고 모든 층을 관통한다. DI는 모든 Bean 연결에, AOP는 Service의 @Transactional에도 Security의 @PreAuthorize에도 적용된다.
① 코어
IoC 컨테이너 (BeanFactory / ApplicationContext)
유일한 중심. Bean의 생명주기(생성 → 의존성 주입 → 초기화 → 소멸)를 관리한다. 나머지 전부가 이것에 의존.
⓪ 환경
실행 환경 — 교체 가능한 슬롯 (증보판에서 갱신)
스프링의 구성요소가 아님. 비웹이면 JVM만으로 충분. 서블릿 웹(WebMVC)이면 Tomcat/Jetty/Undertow 중 택1. 리액티브 웹(WebFlux)이면 Netty 등. → 상세는 02·05장
✕

"IoC 컨테이너 안에 서블릿 컨테이너가 있다" → 포함 관계가 반대다. Tomcat이 가장 바깥이고 그 안에서 스프링 애플리케이션(IoC 컨테이너)이 구동된다. Spring Boot에서 Tomcat이 embedded로 들어오다 보니 "스프링 안에 있는 것"처럼 느껴지지만, 개념적으로는 Tomcat이 요청을 받아 스프링(DispatcherServlet)에게 넘겨주는 관계.

요청이 흐르는 경로 (모듈들의 실제 배치)

[클라이언트 요청]
      │
      ▼
[Servlet Container (Tomcat)]          ← 스프링 외부
      │
      ▼
[Spring Security — FilterChain]       ← DispatcherServlet보다 먼저!
      │                                 서블릿 필터 레벨 (AOP 아님)
      ▼
[Spring WebMVC — DispatcherServlet]   ← Front Controller 패턴
      │   HandlerMapping → Controller → ViewResolver
      ▼
[Service Layer]                       ← @Transactional (AOP 프록시) 적용 지점
      │
      ▼
[Spring Data / JPA / MyBatis]
      │
      ▼
[DataSource → DB]

──────────────────────────────────────────
[IoC Container] 위 모든 컴포넌트(필터 제외)를
Bean으로 등록·관리하는 기반

핵심 문장으로 압축하면:

  • 모듈이 컨테이너 "안에서 동작"하는 게 아니라, 모듈들이 자기 부품을 Bean으로 컨테이너에 맡기는 구조다.
  • 컨테이너는 그릇이 아니라 모든 모듈이 공유하는 조립 공장에 가깝다 — 부품을 생성·연결(DI)·확장(AOP 프록시)해서 돌려준다.
02 — SERVLET & TOMCAT · NEW

서블릿과 톰캣: ⓪층 해부

서블릿은 자바 표준(Jakarta EE 스펙)이 정의한 "HTTP 요청을 처리하는 자바 객체의 규격"이다. 여기서 "규격"과 "처리"가 정확히 뭘 뜻하는지가 이 장의 전부다.

등장인물은 둘: 데이터와 처리기

!

"서블릿 = HTTP 요청이 변환된 DTO 클래스?" → 아니다. 서블릿은 데이터가 아니라 처리기(handler)다. 등장인물이 둘인데 하나로 합쳐서 생긴 혼동:

① 데이터 역할 — HttpServletRequest / HttpServletResponse. 톰캣이 raw HTTP 바이트를 파싱해 만들어주는, 요청 정보를 담은 객체 (DTO에 가까운 역할)
② 처리기 역할 — Servlet. 그 데이터 객체를 인자로 받아서 일하는 쪽

GET /users?id=3 HTTP/1.1        ← raw HTTP 바이트
Host: example.com
      │
      │ 톰캣이 파싱·변환 (①데이터 생성)
      ▼
[HttpServletRequest]             req.getMethod() → "GET"
      │                          req.getParameter("id") → "3"
      │ 인자로 전달하며 호출
      ▼
[Servlet.service(req, res)]      ← ②처리기. 스펙의 핵심 계약
      │
      │ 응답을 채워넣음
      ▼
[HttpServletResponse] ──톰캣이 변환──► raw HTTP 응답 바이트

"규격"이란 인터페이스로 정의된 계약(contract)이라는 뜻이다. 서블릿 스펙의 약속: "HTTP를 처리하고 싶은 클래스는 Servlet 인터페이스를 구현해라. 그러면 어떤 컨테이너든(톰캣이든 Jetty든) 요청이 오면 service()를 호출해주고, 요청 데이터는 HttpServletRequest로 만들어 넘겨주겠다." 스펙은 처리기의 규격(Servlet)과 데이터의 규격(HttpServletRequest/Response) 양쪽을 모두 정의한다 — 톰캣을 Jetty로 바꿔도 동작하는 이유.

톰캣이 정확히 하는 일 5가지

톰캣 = 서블릿 컨테이너 스펙의 구현체. 분해하면:

  • 네트워크 처리 — 포트(8080)를 열고 TCP 연결 수락, HTTP 프로토콜 파싱 (청크 인코딩, keep-alive, 멀티파트, TLS...)
  • 객체 변환 — raw HTTP 바이트 ↔ HttpServletRequest/Response 객체
  • 서블릿 생명주기 관리 — init() → service() → destroy()
  • 스레드 관리 — 요청마다 스레드 풀에서 스레드 배정 (Thread-per-Request 모델 → 05장)
  • 필터 체인 실행 — 서블릿 도달 전 Filter들을 순서대로 통과 (Spring Security가 꽂히는 지점)

여기서 아름다운 대칭 하나: 톰캣은 "서블릿의 IoC 컨테이너"다. 서블릿의 생성·호출·소멸을 개발자 대신 톰캣이 제어한다. 스프링 IoC 컨테이너가 Bean에게 하는 일을, 톰캣은 서블릿에게 한다. 같은 원칙(IoC), 다른 대상.

CHECKPOINT — 제어의 주체
service()를 호출하는 주체는 누구인가?
정답 보기

톰캣(서블릿 컨테이너)이다. 개발자 코드가 서블릿을 호출하는 게 아니라, 컨테이너가 요청을 받아 적절한 서블릿의 service()를 호출한다 — 제어가 프레임워크 쪽에 있다. 그래서 "톰캣은 서블릿의 IoC 컨테이너"라는 문장이 성립한다.

부록: JSP — "톰캣이 대신 짜주는 서블릿"

JSP는 HTML 안에 자바를 심는 템플릿 기술인데, 정체는 서블릿을 자동 생성하는 문법 설탕이다. 톰캣 안의 Jasper 엔진이 users.jsp → users_jsp.java(HttpServlet의 자손, 내용물은 out.println 코드) → .class로 변환·컴파일한다. 첫 요청 때 이 비용이 발생해 첫 페이지가 유독 느렸고, 이게 "옛날 톰캣이 무거웠던" 원인 중 하나. 지금은 Thymeleaf(서블릿 컨테이너 비종속)와 REST+프론트엔드 구조에 밀려 레거시가 됐지만, "자바 웹의 모든 길은 서블릿으로 통한다"는 것을 보여주는 사례로 기억할 가치가 있다 — Controller도 (DispatcherServlet을 통해) 서블릿 위에서 돌고, JSP도 서블릿으로 컴파일된다.

부록 2: "톰캣이 무겁다"는 착시

✕

"톰캣이 무거워서 부팅이 오래 걸린다" → 범인이 다르다. 톰캣 기동 자체는 보통 1초 미만(커넥터 열고 스레드 풀 만드는 정도). 부팅 시간 대부분은 스프링 컨텍스트 초기화 — 클래스패스 스캔, Auto-Configuration 조건 평가, Bean 수백 개 생성+DI+프록시 생성, JPA 메타모델 구축. 로그에서 Tomcat initialized와 Tomcat started 사이의 긴 공백이 전부 스프링(조립 공장)의 시간이다.

착시의 원인: (a) 독립 톰캣 시대(war 배포, web.xml, JSP 컴파일)의 "육중한 WAS" 인상이 각인됨 (b) embedded 시대엔 부팅 로그 처음/끝에 Tomcat이 찍혀 사이의 스프링 시간까지 톰캣 몫으로 보임. 검증: spring.main.lazy-initialization=true로 부팅이 확 빨라지면 범인은 Bean 생성이다.

단, 이 "무거운 부팅"은 결함이 아니라 트레이드오프다. 부팅 때 모든 걸 미리 하는 대가로 런타임이 빠르고 예측 가능해지며(조회만 하면 됨), 설정 오류가 배포 전에 터진다. 이 비용이 치명적인 환경(서버리스)을 위한 해법이 GraalVM Native Image, CRaC 등이다.

03 — SOCKET · NEW

소켓: 요청의 바닥까지

소켓 = 운영체제가 프로그램에게 제공하는 네트워크 통신의 끝점(endpoint). "톰캣이 소켓을 직접 만진다"의 의미를 이해하면 요청 한 개의 일생이 바닥까지 닫힌다.

네트워크의 실체는 랜카드로 들어오는 패킷인데, 프로그램이 직접 다룰 수 없다. OS가 TCP/IP 처리를 해주고 프로그램에게 "여기에 쓰면 상대에게 가고, 여기서 읽으면 상대가 보낸 게 나오는" 창구를 열어준다 — 그게 소켓이다. 파일에 비유하면 정확하다 (리눅스에서 소켓은 실제로 파일 디스크립터다):

파일:  open()   → read()/write()  → close()
소켓:  socket() → recv()/send()   → close()
"네트워크 연결을 파일처럼 읽고 쓴다"
하나의 TCP 연결 = (내 IP:포트 ↔ 상대 IP:포트) 쌍, 연결마다 소켓 하나

"소켓을 직접 만진다" = 이 코드를 담당한다

// 톰캣이 내부에서 하는 일을 날것으로 쓰면
ServerSocket server = new ServerSocket(8080);  // ① 8080에 문 열기

while (true) {
    Socket socket = server.accept();            // ② 연결 수락, 소켓 획득
    InputStream in = socket.getInputStream();   // ③ 바이트 읽기
    // "GET /users HTTP/1.1\r\nHost: ..." ← 생 문자열, 직접 파싱해야 함
    OutputStream out = socket.getOutputStream();// ④ 응답 직접 조립
    out.write("HTTP/1.1 200 OK\r\n...".getBytes());
}

이 ①~④(bind/listen, accept, 바이트 I/O)를 담당하는 것이 "소켓을 만지는" 일이고, 톰캣/Netty가 그 담당자다. 층으로 그리면:

[OS 커널]      TCP/IP 스택, 패킷 처리
   ↕ 소켓 API
[톰캣/Netty]   소켓을 만짐: accept, 바이트 읽기, HTTP 파싱, 객체 조립
   ↕ HttpServletRequest / ServerHttpRequest
[스프링]       소켓의 존재를 모름. 완성된 객체만 받음
   ↕
[Controller]   req.getParameter("id") — 소켓? 그게 뭔데

스프링과 우리가 짜는 코드는 소켓을 한 번도 안 만진다. @RequestParam String id가 어느 소켓에서 어떤 바이트로 왔는지 몰라도 되는 이유 — 톰캣이 그 사이를 전부 흡수했기 때문이다. "톰캣이 별거 안 하는 것 같다"고 느꼈다면, 역설적으로 톰캣이 이 밑바닥을 잘 숨겼다는 증거다.

그리고 이 소켓 관점에서 보면 05장의 스레드 모델 차이도 물리적으로 설명된다: WebMVC(톰캣)는 accept()한 소켓마다 스레드 하나를 전담 배정, WebFlux(Netty)는 소켓들을 논블로킹으로 열어두고 소수 스레드가 "읽을 데이터 생긴 소켓 있어?"를 순회(multiplexing). 두 스택의 차이는 결국 "소켓을 스레드에 어떻게 묶느냐"다.

요청 한 개의 일생 (수직 단면 전체):
전기 신호 → [OS: TCP/IP] → 소켓 → [톰캣: HTTP 파싱]
→ HttpServletRequest → [필터 체인] → [DispatcherServlet]
→ HandlerMapping/Adapter → [Controller POJO] → 응답
04 — DISPATCHERSERVLET · NEW

DispatcherServlet: 국경선과 전화번호부

스프링에서 서블릿 인터페이스의 구현체는 DispatcherServlet 단 하나다. 톰캣 입장에서 보면 그냥 서블릿 하나 — 하지만 스프링 입장에선 서블릿 세계와 POJO 세계 사이의 국경선이다.

✕

"서블릿 인터페이스의 구현체가 Controller" → Controller는 서블릿과 아무 상속 관계가 없는 평범한 Bean(POJO)이다. Servlet을 구현하지도, HttpServlet을 상속하지도 않고, 메서드 시그니처도 service()가 아닌 내 마음대로 만든 것. 스프링의 서블릿 구현체는 DispatcherServlet 하나뿐이며, 요청을 서블릿 세계에서 POJO 세계로 번역해서 Controller에 넘긴다.

톰캣의 세계 (서블릿 스펙)
──────────────────────────────
raw HTTP → HttpServletRequest 생성 → servlet.service() 호출
              │
              ▼
   [DispatcherServlet]   ← 유일한 서블릿 구현체. 여기가 국경선
──────────────────────────────
스프링의 세계 (서블릿 스펙 바깥)
              │
              ▼
   HandlerMapping: "이 URL은 UserController.users() 담당"
              │
              ▼
   HandlerAdapter: HttpServletRequest를 분해해
                   users(Model m)의 파라미터에 맞게 변환 후 호출
              │
              ▼
   [UserController]      ← 그냥 Bean. 서블릿 아님

왜 이렇게 설계했나 — POJO 해방

Controller가 서블릿이었다면: URL마다 서블릿 클래스 작성 + web.xml 등록, 모든 메서드가 (HttpServletRequest, HttpServletResponse) 시그니처로 고정, 파라미터 파싱·변환·응답 조립을 매번 반복. 스프링의 답: "서블릿은 문지기 하나(Front Controller)만 세우고, 진짜 로직은 서블릿 스펙에서 해방된 POJO에게." 그 결과 Controller는 —

  • 톰캣 없이 단위 테스트 가능 (new UserController()로 그냥 생성)
  • 메서드 시그니처를 자유롭게 설계 (@PathVariable Long id, @RequestBody UserDto...)
  • Bean이므로 DI를 받고 AOP 프록시도 적용됨

이것이 01장의 존재 이유(POJO 기반 개발)가 WebMVC에서 실현된 모습이다.

담당자를 어떻게 찾나: 부팅 시 전화번호부 구축

매 요청마다 찾아다니는 게 아니라, 시작 시점에 레지스트리를 만들어두고 요청 시엔 조회만 한다.

[부팅 시 — RequestMappingHandlerMapping]
① IoC 컨테이너에 "Bean 전부 줘" 
② @Controller/@RestController Bean 선별
③ 리플렉션으로 @GetMapping 등 수집
④ 맵 구축:
   { GET  /users      } → UserController.list()
   { GET  /users/{id} } → UserController.detail()
   { POST /orders     } → OrderController.create()
   값 = HandlerMethod (Bean 참조 + Method)

[요청 시 — DispatcherServlet.doDispatch()]
① HandlerMapping 조회: "GET /users/3 담당자?" → detail()
② HandlerAdapter 실행 위임:
   파라미터 분석 → req에서 "3" 추출 → Long 변환 → detail(3L) 호출
③ 반환값 처리:
   @RestController → HttpMessageConverter (객체→JSON)
   뷰 이름 → ViewResolver (JSP/Thymeleaf 등)

Mapping(찾기)과 Adapter(실행)가 분리된 이유: 핸들러 형태가 @Controller 하나가 아니기 때문(HttpRequestHandler, 함수형 라우팅 등). DispatcherServlet은 인터페이스에만 의존하므로 새 스타일이 추가돼도 코드가 안 바뀐다 (OCP, 어댑터 패턴).

얻어갈 통찰: "@GetMapping만 붙이면 연결되는 마법"의 정체 = 부팅 시 리플렉션 스캔 + 런타임 조회. 이 패턴(부팅 시 메타데이터 수집 → 런타임엔 조회만)은 BeanDefinition 등록, AOP 포인트컷 매칭 캐싱 등 스프링 전반에서 반복된다. 그리고 이게 02장 "부팅이 무거운 이유"의 정체이기도 하다.

05 — WEBMVC VS WEBFLUX · NEW

WebMVC vs WebFlux: 톰캣 없이도 되나

"톰캣 없이 웹 스프링을 띄우면 동작 못 하나?" — "톰캣 없이"와 "서블릿 컨테이너 없이"는 다른 말이고, 답은 웹 스택에 따라 갈린다.

세 겹의 "교체 가능"

겹1: 스프링 자체가 웹 없이 돈다
     new AnnotationConfigApplicationContext(...) — 배치/CLI에서 IoC·DI·AOP 완전 동작
     (Spring Batch가 대표 사례. 진짜 필수 기반은 JVM뿐)
겹2: 웹을 해도 서블릿 없이 될 수 있다
     WebFlux는 서블릿 스펙을 안 씀
겹3: 서블릿을 써도 톰캣 없이 된다
     Tomcat / Jetty / Undertow — 서블릿 스펙 구현체 슬롯 (의존성 교체만으로 전환)
!

WebMVC는 서블릿 컨테이너가 필수다 — DispatcherServlet은 이름 그대로 서블릿이라, service()를 호출해줄 컨테이너가 없으면 아무도 깨워주지 않는다. 단 그게 톰캣일 필요는 없다. WebFlux는 서블릿 컨테이너 자체가 불필요 — 자체 추상화(HttpHandler)로 Netty 위에서 돈다. 코어(①)와 메커니즘(②)은 "웹"이라는 개념 자체를 모르므로, 어느 웹 스택을 꽂느냐는 ③층의 선택 문제다.

"WebFlux는 raw HTTP를 처리할 수 있어?" — 질문 교정

✕

WebFlux도 raw HTTP를 직접 파싱하지 않는다. 파싱은 Netty가 한다. 구조가 WebMVC와 대칭이다:

WebMVC:   [Tomcat]  raw HTTP 파싱 → HttpServletRequest → DispatcherServlet(서블릿)
WebFlux:  [Netty]   raw HTTP 파싱 → ServerHttpRequest  → HttpHandler(서블릿 아님)
"누가 밑바닥을 담당하나"만 다를 뿐, 스프링 모듈이 소켓을 만지는 건 둘 다 아니다.
진짜 차이는 파싱이 아니라 → 스레드 모델

핵심 차이: 요청을 스레드에 어떻게 배정하나

WebMVC — Thread-per-Request (1요청 = 1스레드 전담)
요청 A ──→ [스레드 1] ████░░░░░░████   ░ = DB 응답 대기, 스레드는 잠듦
요청 B ──→ [스레드 2] ████░░░░░░████
요청 C ──→ [스레드 3] ████░░░░░░████
           스레드 풀(기본 200)이 바닥나면 요청 D는 줄 서서 대기

WebFlux — Event Loop (소수 스레드가 이벤트 단위 순환)
요청 수만 개 ──→ [이벤트 루프 스레드 4~8개]
    "A의 DB 호출 걸어놓고 → B 처리 → C 처리 → A 응답 왔네? 이어서"
    CPU 코어 수만큼의 스레드가 기다리지 않고 일함

WebMVC의 문제는 대기 시간에도 스레드가 점유된다는 것. WebFlux는 I/O를 걸어놓고 즉시 다음 이벤트로 넘어가 적은 스레드로 수만 동시 연결을 감당한다. 단, 공짜가 아니다 — 전 구간이 논블로킹이어야 하고 코드 스타일이 리액티브 스트림(Mono/Flux)으로 바뀐다.

WebMVCWebFlux
주 목적생산성·단순함적은 자원으로 대규모 동시성
적합한 곳일반 업무 시스템, CRUD, 동시 사용자 수천 이하동시 연결 수만 이상 (게이트웨이·스트리밍·채팅), I/O 대기가 지배적인 중계 계층
치명적 약점대기 중 스레드 낭비 → 초대규모 동시성 한계블로킹 하나가 이벤트 루프 전체를 마비 (JDBC 사용 불가), 디버깅 난이도, 러닝커브
생태계JPA 포함 사실상 전부 호환R2DBC 등 논블로킹 드라이버 필요

기본값은 WebMVC. 안정성·생태계·팀 이해도가 중요한 일반 업무/금융 시스템은 전형적 WebMVC 영역이고, WebFlux는 "스레드 풀로 감당 안 되는 동시 연결"이라는 구체적 문제가 증명됐을 때 꺼내는 도구다 (대표 사례: Spring Cloud Gateway).

정리: 실행 환경 결정표

상황필요한 것
웹이 아님 (배치 등)JVM만 있으면 됨

06 — THREADS, CORES & POOLS · NEW

스레드·코어·커넥션 풀: 숫자들의 근거

CPU 코어 하나는 한 순간에 스레드 하나만 실행한다. 코어 8개면 "진짜 동시"는 8개뿐 — 그런데 톰캣 기본 스레드 풀은 200개다. 이 간극을 이해하면 05장의 스레드 모델이 물리적으로 닫힌다.

왜 코어 8개에 스레드 200개인가 — 대부분 자고 있어서

요청 하나의 처리 시간 (예: 총 100ms)
CPU 계산    ██                    ~10ms  (JSON 파싱, 로직)
I/O 대기    ░░░░░░░░░░░░░░░░░░    ~90ms  (DB 응답, 외부 API 대기)

I/O 대기 중인 스레드는 CPU를 전혀 안 쓴다 — OS가 재워두고(blocked)
코어를 다른 스레드에게 준다. 그래서:
· 스레드 200개가 있어도 그 순간 CPU를 쓰는 건 10~20개
· 나머지는 DB 응답을 기다리며 수면 중
→ 스레드 200개는 "동시에 계산하려고"가 아니라
  "기다리는 동안 자리(예약석)를 지키려고" 있는 것

적정 스레드 수 = 대기/계산 비율이 결정

고전 어림 공식 (Brian Goetz, Java Concurrency in Practice):
적정 스레드 수 ≈ 코어 수 × (1 + 대기시간/계산시간)

예: 8코어, 계산 10ms + 대기 90ms
  → 8 × (1 + 90/10) = 80개
  • CPU 집약 작업(암호화, 이미지 처리) — 대기가 없으니 코어 수 ± α가 최적. 더 늘리면 context switching 비용만 증가
  • I/O 집약 작업(전형적 웹/DB) — 대기 비율만큼 곱해 늘림. 톰캣 기본 200은 "웹은 I/O 대기가 지배적"이라는 가정의 반영이며, 기본값이지 최적값이 아니다

스레드를 무한정 늘릴 수 없는 이유

  • 메모리 — 스레드당 스택 약 1MB(-Xss 기본). 1만 개면 스택만 ~10GB
  • Context switching — 교체마다 레지스터 저장/복원, CPU 캐시 오염. 과도하면 "일하는 시간보다 갈아끼우는 시간"이 커짐
  • 커널 자원 — 자바 스레드는 OS 스레드와 1:1이라 생성·관리가 커널 부담

이것이 05장 WebFlux의 물리적 근거다. 동시 연결 수만 개를 Thread-per-Request로 받으면 비용이 폭발하므로, WebFlux는 대기 자체를 없애 스레드를 코어 수 근처로 줄였다:

WebMVC:   스레드 200개 (대부분 수면 중)   ← 대기를 스레드 점유로 견딤
WebFlux:  이벤트 루프 = 코어 수 × 2 (Netty 기본)  ← 대기 자체를 없앰
절대 기다리지 않는 스레드라면 코어 수만큼만 있어도 CPU를 100% 쓴다
— 잠자는 스레드가 없으니 예약석 200개가 필요 없다

제3의 해법 — 가상 스레드 (Virtual Thread, Java 21+):
OS 스레드 1:1 제약을 깨고 JVM이 수십만 경량 스레드를 소수 OS 스레드에 얹음.
"블로킹 코드를 그대로 쓰면서 WebFlux급 동시성"이 목표.
Boot 3.2+: spring.threads.virtual.enabled=true
→ Thread-per-Request의 한계 자체를 지우는 방향이라 MVC vs Flux 구도를 흔드는 중

커넥션 풀과의 관계 — 그리고 숨은 가정 하나

!

"스레드 200 vs 커넥션 20이면 180개가 커넥션을 기다리며 잠든다" — 이 문장엔 "모든 요청이 DB를 쓰고, 200개가 동시에 몰린 최악 순간"이라는 숨은 가정이 있다. 실제 트래픽은 정적 리소스·헬스체크·캐시 히트·외부 API 위주 요청이 섞여 있으므로, 정확한 병목 조건은:

"스레드 수 > 커넥션 풀"이 아니라 "동시에 커넥션을 원하는 스레드 수 > 커넥션 풀"

DB 사용 요청이 30%라면 200스레드 만석이어도 커넥션 경쟁자는 ~60개다. 다만 CRUD 중심 업무 시스템은 의미 있는 요청 대부분이 DB를 거치므로 이 가정이 근사적으로 성립하는 경우가 많고, 진짜 무서운 건 평시가 아니라 스파이크 순간(트래픽 급증, 슬로우 쿼리가 커넥션을 오래 점유)이다 — 풀 산정은 평균이 아니라 이 순간을 위한 것.

커넥션 풀 산정 — 스레드 공식과 대칭 (가정이 명시적 변수로 들어감):
필요 커넥션 ≈ 동시 활성 스레드 수
             × DB 사용 요청 비율
             × (처리시간 중 커넥션 점유 시간 비율)

예: 100 × 0.5 × 0.4 = ~20개

풀 크기 확장보다 점유 시간 단축이 더 큰 레버인 경우가 많다:

  • @Transactional 범위를 좁게 — 트랜잭션이 열린 동안 커넥션을 물고 있으므로, 트랜잭션 안에서 외부 API 호출이 최악의 패턴 (커넥션을 잡은 채 수백 ms 대기)
  • OSIV(Open Session In View) 끄기 — 켜져 있으면 뷰 렌더링까지 점유가 늘어질 수 있음
  • 슬로우 쿼리 개선이 풀 확장보다 우선

HikariCP 제작자의 유명한 주장도 이 맥락이다 — "풀은 생각보다 작게, 코어 수 × 2 + 디스크 수 정도면 충분한 경우가 많다." DB 서버의 코어도 유한하므로 커넥션이 많다고 처리량이 늘지 않는다. 코어-스레드 관계가 DB 쪽에서 한 번 더 반복되는 것.

한 문장 정리: 스레드가 코어보다 훨씬 많은 이유는 대부분이 대기 중 잠들어 있어서고, 적정 수는 대기/계산 비율이 결정한다. 스레드 풀·커넥션 풀·트랜잭션 범위는 한 세트로 산정해야 하며, 모든 어림 공식은 가정 위에 서 있으므로 가정을 명시하는 순간 진짜 이해가 된다.

07 — STRUCTURE VS MECHANISM

구조 vs 메커니즘: 위치가 있는 것과 없는 것

계층 다이어그램에 DI와 AOP를 하나의 "층"으로 그리면 혼란이 생긴다. 이 둘은 위치가 아니라 작동 방식이기 때문이다.

구분성격예시
구조 (계층) 모듈이 실제로 위치하는 곳. 요청이 통과하는 물리적 순서가 있다. FilterChain → DispatcherServlet → Service → Data 접근 계층
메커니즘 (기능) 특정 층에 속하지 않는 작동 방식. 여러 계층을 관통한다. DI(모든 Bean 연결), AOP 프록시(@Transactional, @PreAuthorize, @Cacheable)
!

Spring Security는 AOP가 아니다. Security의 본체는 DispatcherServlet보다 먼저 실행되는 서블릿 필터 체인이다 — 02장에서 본 톰캣의 "필터 체인 실행"에 꽂히는 것. 다만 @PreAuthorize 같은 메서드 단위 인가는 예외적으로 AOP 프록시 방식을 쓴다 — 하나의 모듈 안에서도 구조(필터)와 메커니즘(프록시)이 함께 쓰이는 사례.

08 — IOC VS DI

IoC vs DI: 원칙과 구현의 관계

IoC(제어의 역전)는 원칙이고, DI(의존성 주입)는 그 원칙을 실현하는 구체적 방법 중 하나다. 상하 관계다.

IoC — 무엇이 "역전"되는가

"제어"란 프로그램의 흐름을 누가 주도하느냐다. 전통 방식에서는 코드가 new PaymentService()처럼 "언제, 어떤 구현체를, 어떻게" 만들지 스스로 결정했다. IoC는 이 결정권을 개발자 코드에서 프레임워크(컨테이너)로 넘기는 것. "필요한 객체는 네가 만들어서 줘, 나는 받아서 쓰기만 할게."

DI — IoC를 실현하는 기법

외부에서 만들어진 객체를 생성자·필드·setter로 주입받는 방식. 스프링의 주력 수단이며, 공식 권장은 생성자 주입(불변성 보장, 순환참조 조기 발견, 테스트 용이성).

!

왜 굳이 둘을 구분하나? IoC를 구현하는 방법이 DI만 있는 게 아니기 때문이다. DL(Dependency Lookup, getBean()으로 직접 요청), 템플릿 메서드/콜백도 전부 "제어가 프레임워크로 넘어갔다"는 점에서 IoC다. 그래서 "IoC/DI"라고 붙여 쓰는 관행은 하나의 축을 개념(IoC)과 대표 구현(DI)으로 함께 부르는 것이다.

✕

"AOP는 개념이고 DI는 그것을 구현하는 방식" → 개념이 섞인 것. DI가 구현하는 것은 AOP가 아니라 IoC다. AOP는 IoC↔DI 쌍과 별개의 독립된 축이며, AOP의 구현은 프록시다. (→ 09장)

그리고 02장에서 발견한 대칭을 여기 다시 연결하면: 이 원칙은 스프링만의 것이 아니다. 톰캣도 서블릿에 대해 IoC를 수행한다 (생성·호출·소멸을 컨테이너가 제어). IoC는 프레임워크라는 것의 보편 원리다.

09 — TWO DIMENSIONS OF IOC

IoC의 두 차원: 객체와 흐름

"스프링에 템플릿 메서드가 있다면 IoC 컨테이너는 DI 말고 다른 방식으로도 구현된 건가?" — 아니다. 여기서 "IoC 컨테이너"와 "IoC 원칙"의 범위를 분리해야 한다.

차원역전되는 것실현 수단담당
객체 차원 객체의 생성·연결·생명주기 DI (주력), DL (보조) IoC 컨테이너
흐름 차원 코드의 실행 흐름·호출 시점 템플릿 메서드, 콜백 JdbcTemplate, RestTemplate 등 개별 클래스

jdbcTemplate.query(sql, rowMapper)에서 커넥션 획득 → SQL 실행 → 예외 변환 → 자원 반납이라는 흐름 전체를 JdbcTemplate이 쥐고 있고, 내 코드(RowMapper)는 프레임워크가 정한 시점에 호출당한다. "Don't call us, we'll call you" — 헐리우드 원칙. 이건 컨테이너 없이 new JdbcTemplate()으로 써도 성립하는, 컨테이너와 무관한 별개 차원의 IoC다.

결론: IoC 컨테이너 자체는 DI(+DL)로 구현된 게 맞다. 템플릿 메서드는 컨테이너의 구현 방식이 아니라, 스프링이 컨테이너 바깥에서도 IoC 원칙을 적용한 또 다른 사례다. (덧붙이면 04장의 서블릿 service()도 흐름 차원 IoC의 사례 — 톰캣이 정한 시점에 호출당하는 콜백이다.)

10 — AOP

AOP: 개념, 그리고 프록시라는 구현

트랜잭션·로깅·보안 같은 횡단 관심사(cross-cutting concern)를 핵심 로직에서 분리한다는 원칙이 AOP. 스프링에서 그 구현은 동적 프록시다.

각 축의 개념-구현 대응표

AXIS 1IoC — 객체 제어권을 프레임워크에 넘긴다
구현DI (주력) · DL · 템플릿/콜백
AXIS 2AOP — 횡단 관심사를 핵심 로직에서 분리한다
구현동적 프록시 — 인터페이스가 있으면 JDK Dynamic Proxy, 없으면 CGLIB
개입 지점BeanPostProcessor(AnnotationAwareAspectJAutoProxyCreator)가 Bean 초기화 시점에 원본을 프록시로 교체

두 축은 서로 별개지만 서로를 이용한다 — AOP의 프록시 교체는 IoC 컨테이너의 Bean 생성 과정에 끼어들어 작동한다. 다만 의존한다고 해서 상하 관계인 건 아니다. AOP가 IoC 컨테이너를 이용하지만 AOP가 IoC의 구현인 건 아니다.

Bean 생성 과정에 AOP가 끼어드는 시점:

Bean 인스턴스화 → 의존성 주입(DI)
   → postProcessBeforeInitialization
   → 초기화 콜백
   → postProcessAfterInitialization
        └─ 여기서 원본 Bean → 프록시로 교체!
   → 컨테이너가 프록시를 반환

그래서 우리가 주입받는 @Transactional Bean은
사실 원본이 아니라 프록시다.
CHECKPOINT — 프록시 구조 이해 확인
같은 클래스 안에서 this.order()로 내부 호출하면 @Transactional이 적용될까?
정답 보기

적용되지 않는다. 트랜잭션은 프록시가 메서드 호출을 가로채면서 시작되는데, this.order()는 프록시를 거치지 않고 원본 객체의 메서드를 직접 부르는 것이기 때문이다.

외부에서 들어오는 호출: 클라이언트 → [프록시: tx.begin] → 원본.order() → [프록시: tx.commit]

내부 호출: 원본.method() → this.order() — 프록시가 개입할 틈이 없다.

이것이 "스프링 AOP는 프록시 기반이라 자기 호출(self-invocation)에는 어드바이스가 적용되지 않는다"는 대표적 한계이며, 프록시 구조를 이해했는지 확인하는 단골 포인트다.

11 — @TRANSACTIONAL DISSECTED

@Transactional 해부: 두 축의 협력

"@Transactional은 AOP 아니야?" — 맞다, AOP로 동작한다. 동시에 기술 추상화의 대표 사례이기도 하다. 모순이 아니라 하나의 기능을 두 축이 나눠 담당하는 것.

추상화무엇을 감췄나

@Transactional 어노테이션과 그 뒤의 PlatformTransactionManager 인터페이스. 밑에서 JDBC를 쓰면 DataSourceTransactionManager, JPA면 JpaTransactionManager가 실제 커밋/롤백을 수행한다. 기술을 바꿔도 내 코드는 그대로 — 기술 종속성 제거.

AOP어떻게 끼어드나

그 트랜잭션 로직을 내 메서드 앞뒤에 붙이는 전달 수단이 프록시다. BeanPostProcessor가 초기화 시점에 Bean을 프록시로 교체해뒀기 때문에, 트랜잭션 코드를 한 줄도 안 썼는데 적용된다.

클라이언트 → [프록시] tx.begin()
                  → [진짜 order()]
              tx.commit() or rollback()

비유: 추상화는 "표준 콘센트 규격",
AOP는 "그 콘센트까지 전기를 배달하는 배선".
@Transactional은 콘센트에 꽂는 플러그.

이 패턴 — 추상화된 어노테이션 + AOP 프록시 전달 — 은 @Cacheable, @Async, @PreAuthorize에서도 동일하게 반복된다. 이 구조가 보이기 시작하면 스프링 어노테이션 대부분의 동작 원리를 한 번에 꿰게 된다.

12 — PSA IN ITS PLACE

PSA의 진짜 위상: 엔진이 아니라 설계 철학

결론부터: PSA는 IoC·AOP와 같은 위상이 아니다. 대화 초반에 "3대 축"으로 나란히 놓았던 것을 여기서 최종 교정한다.

✕

"스프링의 3대 요소는 IoC/DI, AOP, PSA (공식 분류처럼 단정)" → PSA는 스프링 공식 문서의 표준 용어가 아니다. 공식 레퍼런스는 IoC Container, AOP, Transaction Abstraction 식으로 기능을 나열할 뿐이다. "PSA"라는 묶음은 한국 스프링 교육 생태계(토비의 스프링 등)에서 정착된 교육용 정리 방식이다. 다만 개념 자체 — 기술을 갈아끼워도 코드가 안 변하는 추상화 계층 — 는 실재하는 중요한 설계 특징이 맞다. 이름표가 비공식일 뿐.

위상을 가르는 세 가지 기준

기준IoC / AOPPSA
없으면 무너지나? 컨테이너가 없으면 스프링이 아니고, AOP가 없으면 선언적 프로그래밍 모델(@Transactional 등)이 통째로 붕괴 없어도 스프링은 스프링. 각 기술을 직접 다루면 불편해질 뿐
고유 엔진이 있나? 있음 — Bean 생명주기 엔진, 프록시 생성·어드바이스 체인 없음 — 인터페이스+구현체(전략 패턴)일 뿐, 동작은 AOP 프록시에 얹혀 이뤄짐
위에 뭔가 세워지나? 모듈 전체가 이 위에 세워짐 PSA 자체가 IoC/AOP 위에 세워진 결과물

IoC, AOP = 엔진(메커니즘). PSA = 그 엔진으로 만들어낸 설계 철학의 산물(좋은 인터페이스 설계 + 전략 패턴). 층이 다르다. 공부 전략으로 번역하면 — IoC/AOP는 내부 동작·확장점·한계까지 파야 하고, PSA는 트랜잭션 추상화를 공부할 때 "이런 추상화 설계 패턴을 스프링 전반에서 반복하는구나" 하고 관점 하나 얻고 지나가면 끝인 10분짜리 개념이다.

참고로 이 관점은 실행 환경에서도 확인된다 — 05장의 "톰캣↔Jetty 교체, WebMVC↔WebFlux 교체가 코드에 영향 없음"이 바로 이 추상화 설계 철학이 ⓪층에 적용된 모습이다. 스프링은 "서블릿 스펙"에 의존하지 "톰캣"에 의존하지 않는다.

같은 지원 메커니즘 층에 있는 것들

교육용 3축에서 빠지곤 하지만 실제로 존재하는, 코어가 제공하는 지원 메커니즘들 — 순서대로 정복할 필요 없이 코어 공부 중 마주칠 때마다 하나씩 줍는 방식이 효율적이다:

  • 이벤트 (ApplicationEvent, @EventListener) — Bean 간 결합도를 낮추는 발행/구독
  • Environment / Resource 추상화 — 프로파일·프로퍼티 통합, 파일/클래스패스/URL 동일 취급
  • @Profile / @Conditional — 환경별 조건부 Bean 구성. Boot의 Auto-Configuration이 이 위에 세워짐
  • ConversionService / Validator — 타입 변환·데이터 바인딩의 기반
  • SpEL — @Value("#{...}") 등의 표현식 엔진
13 — SPRING BOOT

Spring Boot: 무엇을 자동화했나

부트는 스프링을 "대체"하거나 "새 기능을 추가"한 게 아니라, 스프링을 쓰기 위한 준비 과정을 자동화한 것이다.

확장 영역프레임워크만 쓸 때Boot가 해주는 것
설정 DataSource, 트랜잭션 매니저, DispatcherServlet 전부 수동 설정 Auto-Configuration — 클래스패스를 보고 "JPA 있네? 이렇게 설정해줄게" (내부는 @Conditional 메커니즘)
의존성 라이브러리 버전 조합을 직접 관리 (충돌 지옥) Starter — spring-boot-starter-web 하나로 궁합 맞는 조합을 통째로
실행 war를 만들어 외부 Tomcat에 배포 Embedded Tomcat — java -jar로 즉시 실행 (Jetty/Undertow로 의존성 교체 가능 → 05장)
운영 헬스체크·메트릭 직접 구축 Actuator — 기본 제공 (부팅 시간 분석용 /startup 엔드포인트도 여기) 
[Spring Boot]       = 실행·설정 자동화 껍데기
   └─ [Spring Framework]  = 실제 일하는 본체 (Core + 모듈들)

비유: 프레임워크가 "부품이 다 들어있는 조립식 PC 세트"라면,
부트는 "조립·OS 설치까지 끝낸, 전원만 누르면 되는 완제품 PC".
안에 든 부품은 동일하다.

그래서 @Transactional을 쓰면 그건 프레임워크(AOP + 트랜잭션 추상화)의 기능이고, 그게 별 설정 없이 바로 작동하는 건 Boot(Auto-Configuration) 덕분 — 이렇게 역할이 나뉜다. 이 둘을 섞어 말하지 않는 것이 정확한 이해의 지표다.

14 — ERRATA

오답노트: 정정 사항 총정리

대화 중 잘못 이해했거나 헷갈렸던 지점의 최종 정리. 8번부터가 서블릿·톰캣 편에서 추가된 항목이다.

#틀린/헷갈린 이해바른 이해
1 서블릿 컨테이너가 IoC 컨테이너 안에 있다 반대. Tomcat(서블릿 컨테이너)이 가장 바깥이고, 스프링은 그 위에 올라타는 프레임워크. Tomcat은 스프링의 구성요소가 아니다.
2 AOP는 개념, DI는 그 구현 DI가 구현하는 것은 IoC. AOP는 별개의 축이며 AOP의 구현은 동적 프록시(JDK Proxy / CGLIB).
3 템플릿 메서드가 있으니 IoC 컨테이너는 DI 외의 방식으로도 구현된 것 컨테이너 자체는 DI(+DL)로 구현. 템플릿/콜백은 컨테이너와 무관한 흐름 차원의 IoC — 원칙의 또 다른 적용 사례.
4 @Transactional은 AOP다 (단일 소속) 둘 다다. 겉모습(인터페이스)은 기술 추상화, 전달 방식은 AOP 프록시. 하나의 기능을 두 축이 협력해 만든다.
5 IoC/DI, AOP, PSA가 공식 3대 요소 PSA는 공식 용어가 아닌 교육용 정리(한국 생태계에서 정착). 논쟁의 여지 없는 코어는 IoC 컨테이너와 AOP 두 개. PSA는 그 엔진으로 만든 설계 철학의 산물로, 지원 메커니즘 층에서 관점으로 익히면 충분.
6 모듈이 컨테이너 안에서 동작한다 모듈이 자기 부품을 Bean으로 컨테이너에 맡기는 구조. 컨테이너는 그릇이 아니라 공유 조립 공장.
7 Spring Security도 AOP로 동작 본체는 서블릿 필터 체인(DispatcherServlet 앞단). @PreAuthorize 같은 메서드 보안만 예외적으로 AOP 프록시 사용.
8 서블릿 = HTTP 요청이 변환되는 DTO 클래스 서블릿은 데이터가 아니라 처리기(handler)의 규격. 요청 데이터가 담기는 객체는 별도의 HttpServletRequest이며, 서블릿은 그것을 인자로 받아 일한다.
9 서블릿 인터페이스의 구현체가 Controller 스프링의 서블릿 구현체는 DispatcherServlet 단 하나. Controller는 서블릿과 상속 관계가 없는 POJO Bean이고, HandlerAdapter가 서블릿 세계 → POJO 세계로 번역해서 호출해준다.
10 톰캣이 무거워서 부팅이 느리다 톰캣 기동은 보통 1초 미만. 부팅 시간의 진범은 스프링 컨텍스트 초기화(스캔, Bean 생성, DI, 프록시, JPA 메타모델). 다만 이는 런타임 안정성을 위한 트레이드오프.
11 톰캣 없으면 웹 스프링은 동작 불가 세 겹으로 갈린다: 비웹이면 JVM만으로 충분 / WebMVC면 서블릿 컨테이너 필요하되 Tomcat↔Jetty↔Undertow 교체 가능 / WebFlux면 서블릿 컨테이너 자체가 불필요(Netty).
12 WebFlux는 raw HTTP를 직접 처리한다 파싱은 Netty가 한다 (WebMVC에서 톰캣이 하듯). 두 스택의 진짜 차이는 파싱이 아니라 스레드 모델 — Thread-per-Request vs Event Loop, 즉 "소켓을 스레드에 어떻게 묶느냐".
13 "스레드 200 > 커넥션 20이면 180개가 커넥션 대기로 잠든다" (무조건) "전 요청이 DB를 쓴다"는 숨은 가정이 있는 문장. 정확한 병목 조건은 "동시에 커넥션을 원하는 스레드 수 > 커넥션 풀"이며, DB 사용 비율·점유 시간 비율이 명시적 변수로 들어가야 한다. 단 CRUD 중심 시스템에선 근사적으로 성립.
15 — ROADMAP

학습 로드맵

위상 정리에서 도출된 학습 순서. ⓪층(실행 환경)은 이번 증보로 완료 — 이제 코어 두 엔진으로.

⓪층: 실행 환경 — 완료

소켓 → 톰캣(서블릿 컨테이너) → 서블릿 스펙 → DispatcherServlet 국경선 → WebMVC/WebFlux 갈래까지. 요청 한 개의 일생이 바닥까지 닫혔다.

IoC 컨테이너 내부

BeanDefinition 로딩 → 인스턴스화 → 의존성 주입 → 초기화까지의 생명주기. 확장점(BeanPostProcessor, BeanFactoryPostProcessor)이 핵심. "부팅이 오래 걸리던 그 시간에 벌어지는 일"의 정체.

AOP 프록시 메커니즘

1번의 BeanPostProcessor를 알면 자연스럽게 연결. JDK Dynamic Proxy vs CGLIB, 그리고 self-invocation 같은 프록시의 한계까지.

지원 메커니즘 (필요할 때 줍기)

트랜잭션 추상화를 이때 만나면 "프록시 + 추상화 조합"이 저절로 보인다. 이벤트, @Conditional, SpEL 등은 코어 공부 중 마주칠 때마다 하나씩.

모듈 (WebMVC → Security → Data)

WebMVC의 HandlerMapping/Adapter 뼈대는 이미 04장에서 선행 학습됨. ArgumentResolver·HttpMessageConverter 등 세부를 채우고, Security 필터 체인 내부로.

마지막으로, 이 문서 전체를 한 문장으로:

POJO로 개발하게 해주는 것이 스프링의 목적이고, 그 수단이 IoC 컨테이너(→DI)와 AOP(→프록시)라는 두 엔진이며, 그 엔진으로 트랜잭션 추상화 같은 지원 메커니즘들을 빚어냈고, 그 위에 WebMVC·Security·Data 모듈이 얹힌다. 이 전체는 교체 가능한 실행 환경 위에서 돈다 — 소켓을 만지는 밑바닥(톰캣/Netty)이 raw HTTP를 객체로 바꿔주면, DispatcherServlet이라는 국경선에서 스프링의 POJO 세계가 시작된다. Boot는 이 조립 공장의 초기 세팅을 자동화한 껍데기다.
