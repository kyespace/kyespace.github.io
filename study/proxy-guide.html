Study Guide — Proxy Internals

모든 호출은 배선반을 거친다

JDK 동적 프록시와 CGLIB이 내부적으로 어떻게 호출을 가로채는지, 왜 요즘은 CGLIB이 기본값이 됐는지, 그리고 그 밑바탕에 있는 GoF Proxy 패턴까지 — 나눴던 질문들을 순서대로 정리했습니다.

UserService
save()
invoke()
@Around
target
비유: 프록시는 전화 교환원, InvocationHandler는 교환원이 들고 있는 매뉴얼입니다. 메서드 호출(전화)이 오면 교환원은 항상 매뉴얼을 먼저 보고, 거기 적힌 순서대로 진짜 대상(부장님)에게 연결합니다.
① 왜 프록시가 필요한가

대리인을 세우는 이유

원본 코드를 건드리지 않고, 호출 앞뒤에 공통 로직을 끼워넣기 위함

트랜잭션, 로깅, 보안 체크 같은 횡단 관심사(cross-cutting concern)를 모든 메서드에 직접 작성하면 중복이 폭발합니다. 그래서 스프링은 진짜 객체 앞에 대리인(프록시)을 세워두고, 그 대리인이 호출을 가로채서 부가 로직을 자동으로 끼워넣게 만듭니다.

스프링 컨테이너가 빈을 만들 때, @Transactional·@Around 같은 것과 매칭되는 빈이 있으면 원본 객체 대신 그걸 감싸는 프록시 객체를 만들어 그 프록시를 진짜 빈으로 등록합니다. 매칭되는 게 없으면 원본 객체가 그대로 빈이 됩니다.

② JDK 동적 프록시

기존 인터페이스를 구현하는 새 클래스

인터페이스가 있을 때만 동작 — 상속이 아니라 위임(delegation)

1 핵심 오해 정정

JDK 동적 프록시는 새 인터페이스를 만드는 게 아닙니다. 원래 있던 인터페이스(UserService)를 그대로 구현하는 새로운 클래스를 런타임에 만드는 것입니다. 자식 클래스를 만드는 CGLIB과 반대로, 상속이 아니라 같은 인터페이스를 구현하는 별개의 클래스입니다.

2 두 가지 구성요소

java.lang.reflect.Proxy — 인터페이스를 구현하는 프록시 클래스를 런타임에 생성하는 자바 표준 팩토리

InvocationHandler — 자바 표준 라이브러리의 인터페이스. 프록시의 모든 메서드 호출이 도착하는 단 하나의 창구. 스프링에서는 JdkDynamicAopProxy라는 클래스가 이걸 구현하고 있음 (개발자가 직접 구현하지 않음)

3 생성 순서

1단계 스프링이 핸들러 생성 → JdkDynamicAopProxy(진짜 대상 + 매칭된 어노테이션 정보를 담고 있음) 2단계 그 핸들러를 재료로 → Proxy.newProxyInstance(classLoader, [UserService.class], handler) 3단계 결과 → UserService를 구현하는 프록시 객체 완성, 이게 컨테이너에 빈으로 등록됨

4 호출 시점 동작

// 프록시의 save()는 로직이 없고 무조건 invoke로 위임
proxy.save(user)
    → handler.invoke(proxy, saveMethod, args)
        → [어노테이션 코드 앞부분] (@Before, @Around 진입부)
        → method.invoke(target, args)  // 진짜 UserServiceImpl.save() 실행 (리플렉션)
        → [어노테이션 코드 뒷부분] (@After, @Around 나머지)

필수 조건: 대상이 인터페이스를 구현하고 있어야만 동작합니다. 인터페이스가 없으면 이 방식 자체가 불가능합니다.

③ CGLIB

대상 클래스를 상속하는 자식 클래스

Code Generation LIBrary — 인터페이스 없이도 동작

1 동작 방식

CGLIB은 대상 클래스(UserServiceImpl) 자체를 상속하는 자식 클래스를 바이트코드 조작으로 런타임에 만듭니다. 그 자식 클래스에서 메서드를 오버라이드해서, 그 안에서 부가 로직을 실행한 뒤 super.method()로 진짜 로직을 호출합니다.

class UserServiceImpl$$CGLIB extends UserServiceImpl {
    @Override
    public void save(User user) {
        // [어노테이션 코드 앞부분]
        super.save(user);   // 직접 바이트코드 호출 (리플렉션 아님)
        // [어노테이션 코드 뒷부분]
    }
}

2 제약사항

상속 기반이라 final 클래스·final 메서드는 프록시 불가(오버라이드 자체가 안 됨), private 메서드도 프록시 대상에서 제외됩니다. 과거엔 기본 생성자가 필요했지만, 최신 CGLIB(Objenesis 사용)은 이 제약도 우회 가능합니다.

④ 나란히 비교

구현 vs 상속

JDK 동적 프록시
  • 구조: 인터페이스 구현 (위임)
  • 실행 위치: InvocationHandler.invoke() 안에서 전후 실행
  • 대상 호출: 리플렉션 (method.invoke)
  • 필수 조건: 인터페이스 반드시 필요
CGLIB
  • 구조: 클래스 상속 (오버라이드)
  • 실행 위치: 오버라이드 메서드 안에서 super.method() 전후 실행
  • 대상 호출: 직접 바이트코드 호출 → 미세하게 더 빠름
  • 필수 조건: 인터페이스 불필요, final만 아니면 됨
⑤ 왜 요즘은 CGLIB이 기본값인가

proxyTargetClass = true

Spring Boot 2.x부터 AOP 자동설정의 proxyTargetClass 기본값이 true로 바뀌었습니다. 그 결과 인터페이스가 있든 없든 CGLIB이 기본으로 선택됩니다.

배경: 예전엔 "인터페이스 있으면 JDK 프록시"가 기본이었지만, 실무에서 인터페이스 없이 구현 클래스만 빈으로 등록하는 스타일이 흔해지면서(구현체가 하나뿐인 경우가 대부분, Mockito로 클래스 자체를 목킹 가능) 일관성을 위해 CGLIB로 통일된 것입니다.

성능 차이는 현재 버전들에서 체감될 정도는 아니며, 선택 기준은 성능보다 일관성(모든 빈이 같은 방식으로 프록시되게)입니다.

⑥ 흔한 함정

Self-Invocation 문제

프록시를 거치지 않으면 AOP는 작동하지 않는다

컨테이너에 등록되고 @Autowired로 주입되는 건 원본이 아니라 프록시입니다. 외부에서 프록시를 거쳐 호출하면 AOP가 걸리지만, 클래스 내부에서 자기 자신을 호출(this.method())하면 프록시를 거치지 않고 원본 객체끼리 직접 호출해버립니다.

@Service public class UserService { @Transactional public void outer() { this.inner(); // ← this는 프록시가 아니라 원본 객체 자신 } @Transactional public void inner() { // 트랜잭션 적용 안 됨! } }

외부 → userServiceBean.outer() 는 프록시를 거치므로 ✅ 정상 적용되지만, outer() 내부의 this.inner()는 invoke() 자체를 거치지 않으므로 어노테이션 매칭 로직이 실행되지 않습니다.

해결책 (참고) 메서드를 별도 빈으로 분리하기 · AopContext.currentProxy()로 현재 프록시 얻기 · 자기 자신을 @Autowired로 셀프 주입하기

✕ AspectJ 위빙은 이 문제가 없음

스프링 AOP는 런타임 프록시 방식을 택해서 self-invocation 문제가 생기지만, AspectJ는 컴파일/로드 타임에 바이트코드 자체를 조작(위빙)해서 끼워넣기 때문에 프록시가 아예 필요 없고 이 문제도 없습니다.

⑦ GoF와의 연결

AOP ⊃ 프록시 패턴

AOP는 횡단 관심사를 분리한다는 개념/패러다임이고, 프록시 패턴은 그걸 자바에서 구현하는 실제 기술적 수단 중 하나입니다. AOP를 구현하는 방법이 프록시만 있는 건 아니며, AspectJ 위빙이 그 다른 예입니다.

패턴목적스프링 AOP와의 관계
Proxy (GoF)실제 객체에 대한 접근을 제어관례적으로 스프링이 "프록시"라 부르는 근거
Decorator (GoF)기능을 추가구조는 Proxy와 거의 동일, 실질적 의도는 스프링 AOP가 이쪽에 더 가까움

스프링 AOP는 "접근 제어"가 아니라 "부가 기능 삽입"이 목적이라, GoF 기준으로는 사실 Decorator 패턴에 더 가까운 변형인데 관례적으로 Proxy라 불립니다.

핵심 요약
  1. JDK 동적 프록시는 인터페이스를 구현하는 새 클래스를 만들고, InvocationHandler.invoke()라는 단일 창구를 거쳐 리플렉션으로 대상을 호출한다.
  2. CGLIB은 대상 클래스를 상속하는 자식 클래스를 만들고, 오버라이드한 메서드 안에서 super.method()를 직접 호출한다.
  3. Spring Boot는 proxyTargetClass=true가 기본값이라 CGLIB이 사실상 기본이며, 이유는 성능이 아니라 일관성이다.
  4. AOP는 반드시 프록시를 거쳐야 작동하므로, self-invocation(this.method())에서는 걸리지 않는다.
  5. 스프링 AOP의 "Proxy"라는 이름은 관례이며, 의도상으로는 GoF의 Decorator에 더 가깝다.
