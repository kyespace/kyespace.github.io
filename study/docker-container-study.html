01

VM vs Container — 핵심 차이

가장 근본적인 차이는 OS 커널을 공유하느냐, 격리하느냐입니다.

🖥 Virtual Machine
  • 각 VM이 Guest OS 전체를 포함
  • Hypervisor가 하드웨어 가상화
  • 부팅 시간: 수십 초 ~ 수 분
  • 이미지 크기: 수 GB 단위
  • 격리 수준: 강력 (완전한 OS 분리)
  • 오버헤드: CPU/메모리 상당히 큼
📦 Docker Container
  • 호스트 OS 커널을 공유
  • Namespace / cgroup으로 격리
  • 부팅 시간: 밀리초 ~ 수 초
  • 이미지 크기: 수 MB ~ 수백 MB
  • 격리 수준: 프로세스 수준
  • 오버헤드: 거의 없음 (네이티브에 근접)

격리 기술: Namespace & cgroup

🔒 Linux Namespace
  • pid: 프로세스 ID 공간 격리
  • net: 네트워크 인터페이스 격리
  • mnt: 파일시스템 마운트 격리
  • uts: 호스트명 격리
  • ipc: 프로세스간 통신 격리
  • user: UID/GID 공간 격리
⚡ cgroup
  • CPU 사용량 제한
  • 메모리 상한 설정
  • 디스크 I/O 스로틀링
  • 네트워크 대역폭 제어
  • 자원 사용 모니터링
📁 Union File System
  • OverlayFS (현재 기본 드라이버)
  • 여러 레이어를 하나로 병합
  • 읽기 전용 레이어 공유
  • CoW(Copy-on-Write) 방식
✅ 핵심 포인트 Container는 VM처럼 OS를 복제하지 않습니다. 호스트 Linux 커널을 그대로 씁니다. Docker for Mac/Windows에서는 내부적으로 경량 Linux VM을 띄워 그 위에서 컨테이너를 실행합니다.

03

레이어(Layer) 개념

Docker 이미지는 불변(immutable) 레이어들의 스택입니다. Dockerfile의 각 명령어(RUN, COPY, ADD)는 새로운 레이어를 생성합니다.

Dockerfile
FROM   ubuntu:22.04          # Layer 0: base image
RUN    apt-get install -y java # Layer 1: java 설치
COPY   . /app                # Layer 2: 소스 복사
RUN    ./gradlew build        # Layer 3: 빌드
CMD    ["java", "-jar", "app.jar"] # 메타데이터 (레이어 아님)

레이어 스택 구조

R/W
Container Layer

READ / WRITE
⬇ 아래는 모두 Read-Only

03-B

Container Layer · OverlayFS 구조

Container Layer는 컨테이너 프로세스가 아니라, 그 컨테이너가 파일시스템에 뭔가 쓸 때 실제로 기록되는 전용 쓰기 공간입니다. 컨테이너가 100개 뜨면 이미지 레이어는 공유되고, Container Layer만 100개 생깁니다.

OverlayFS 세 가지 개념

📂 lower
  • 읽기 전용 이미지 레이어들
  • 변경 불가 — 항상 원본 유지
  • 여러 컨테이너가 공유
✏️ upper
  • Container Layer (R/W)
  • 실제 변경사항이 기록되는 곳
  • 이 컨테이너 전용
👁 merged
  • lower + upper를 합쳐서 보여주는 가상 뷰
  • 컨테이너 안에서 보이는 파일시스템
  • 실제로 합치는 작업 없음 — 조회 시 실시간 결정
실제 디스크 디렉터리 구조
/var/lib/docker/overlay2/
  ├── abc123/          # 레이어 1 (ubuntu base)
  │   └── diff/        # 이 레이어의 변경분만
  │       ├── bin/
  │       ├── etc/
  │       └── usr/
  │
  ├── def456/          # 레이어 2 (java 설치)
  │   └── diff/
  │       └── usr/lib/jvm/   # java로 생긴 파일들만
  │
  ├── ghi789/          # 레이어 3 (COPY . /app)
  │   └── diff/
  │       └── app/           # 복사된 소스 파일들만
  │
  └── mno345/          # Container Layer (R/W)
      ├── diff/        # 컨테이너가 실제로 쓴 변경분
      ├── merged/      # 모든 레이어 합친 뷰 (컨테이너가 보는 것)
      ├── upper/       # diff와 동일 (쓰기 대상)
      └── lower        # 아래 레이어들 참조 링크
💡 파일 탐색 순서 컨테이너 안에서 파일을 읽을 때 OverlayFS는 upper(최신) → L3 → L2 → L1 → L0(베이스) 순으로 탐색합니다. 가장 먼저 발견된 레이어의 파일이 사용됩니다. 같은 경로가 여러 레이어에 있으면 위쪽(최신) 레이어가 아래를 가립니다(shadow).
03-C

파일 추가·수정·삭제 — 실제 동작

lower는 읽기 전용이라 직접 건드릴 수 없습니다. OverlayFS는 세 가지 상황을 각각 다르게 처리합니다.

① 파일 추가

파일 추가
# 컨테이너 안에서
$ touch /app/new.txt

# OverlayFS 내부 동작
upper/app/new.txt  ← upper에 파일 생성
lower/             ← 그대로
merged/app/new.txt ← upper + lower 합쳐진 뷰에서 보임

② 파일 수정 — Copy-on-Write (CoW)

파일 수정 (CoW)
# config.yaml 은 lower L2에 존재하는 파일
$ echo "new" > /app/config.yaml

# OverlayFS 내부 동작
1. lower L2의 config.yaml을 upper로 복사   ← CoW 발생
2. upper의 config.yaml 수정 적용
3. merged에서는 upper 버전이 lower를 가림

lower L2/app/config.yaml  ← 원본 그대로 유지
upper/app/config.yaml     ← 수정된 버전 (여기서 읽힘)

③ 파일·디렉터리 삭제 — Whiteout

lower는 지울 수 없습니다. 대신 OverlayFS는 whiteout이라는 특수 마커 파일을 upper에 생성해 해당 파일을 merged 뷰에서 숨깁니다.

파일/디렉터리 삭제 (Whiteout)
# 컨테이너 안에서
$ rm /etc/config/settings.conf
$ rm -rf /etc/config/

# OverlayFS 내부 동작
upper/.wh.settings.conf   ← whiteout 마커 (크기 0, 특수 파일)
upper/.wh..wh..opq        ← 디렉터리 통째 삭제 마커 (opaque whiteout)

# merged 뷰 구성 시
upper에 .wh.파일명 존재 → lower의 해당 파일 숨김
lower의 실제 파일은 여전히 존재 (컨테이너에서만 안 보임)

세 가지 동작 요약

① 파일 추가
upper에
파일 생성

lower 변화 없음
② 파일 수정
lower → upper
CoW 복사 후
upper에서 수정
lower 원본 유지
③ 파일 삭제
upper에
.wh.파일명
마커 생성
lower 원본 유지
어떤 경우에도 lower(이미지 레이어)는 절대 변경되지 않습니다
03-D

레이어 = diff 스냅샷 · 레이어 해시

레이어는 특별한 바이너리 포맷이 아닙니다. 그 명령어가 파일시스템에 가한 변경분(diff)을 담은 일반 리눅스 디렉터리 트리입니다.

레이어 하나의 실제 내용

레이어 구성 요소
# 레이어 = 아래 네 가지의 집합

1. 파일 바이너리   # 실제 파일 내용
   /usr/lib/jvm/java-17/bin/java  (실행 바이너리)
   /app/Main.class                (컴파일 결과물)

2. 파일 경로       # 어느 위치에 있는 파일인지
   /usr/lib/jvm/java-17/bin/java

3. 메타데이터      # 파일 속성
   권한: chmod 755
   소유자: uid=0, gid=0
   타임스탬프: 2024-01-01T00:00:00Z

4. Whiteout 마커   # 삭제 표시
   .wh.deleted_file
   .wh..wh..opq    (디렉터리 통째 삭제)

RUN 명령어 실행 후 레이어 확정 과정

RUN apt-get install java 실행
upper에 /usr/lib/jvm/... 파일들 생성됨
⬇ 명령어 완료
upper의 내용을 새 레이어(L1)로 확정
/var/lib/docker/overlay2/def456/diff/ 로 저장
⬇
다음 명령어는 L1을 lower로 삼아 시작
COPY . /app → upper에 소스 파일들 생성 → L2로 확정...

레이어 해시 계산

레이어 ID = SHA256 해시
레이어 ID = SHA256(
  모든 파일 경로        +
  모든 파일 바이너리 내용 +
  모든 파일 메타데이터  +
  부모 레이어 해시
)

# 파일 하나라도 바뀌면 해시가 달라짐 → Cache MISS
# 완전히 동일하면 해시 일치 → Cache HIT → 재사용

# 실제 레이어 해시 확인
$ docker image inspect myapp --format='{{json .RootFS.Layers}}'
[
  "sha256:a3ed95caeb02...",  # L0
  "sha256:9f16d3c8bc73...",  # L1
  "sha256:f2e4e8c7a1b9..."   # L2
]
✅ 레이어 한 줄 정의 레이어 = 파일 바이너리 + 경로 + 메타데이터 + whiteout 마커의 집합. 특별한 포맷 없이 그냥 리눅스 디렉터리 트리 그대로입니다. Dockerfile 명령어 하나 실행 후 변경된 파일시스템의 diff 스냅샷입니다.
04

레이어 캐시 (Cache Hit / Miss)

Docker는 빌드 시 각 레이어를 SHA256 해시로 식별합니다. 동일한 명령어 + 동일한 입력이면 캐시를 재사용하고, 하나라도 바뀌면 그 이후 레이어를 모두 다시 빌드합니다.

🔍
레이어 식별자 계산명령어 문자열 + 부모 레이어 해시 + (COPY/ADD의 경우) 파일 내용 체크섬 조합
✅
Cache HIT — 기존 레이어 재사용해시가 로컬 캐시에 존재 → 빌드 시간 대폭 절감
❌
Cache MISS — 레이어 재빌드해시 불일치 → 해당 레이어부터 이후 모든 레이어 연쇄 재빌드
⚠️ 캐시는 위에서 아래로 전파 중간 레이어 하나가 바뀌면 그 아래 모든 레이어의 캐시가 무효화됩니다. 자주 바뀌는 것은 Dockerfile 아래쪽에 배치하세요.
✅ 좋은 패턴 — 의존성 먼저, 소스는 나중에
FROM openjdk:17
RUN  apt-get install -y curl wget     # HIT: 거의 변하지 않음
COPY build.gradle settings.gradle /app/
RUN  cd /app && ./gradlew dependencies # HIT: build.gradle 변경 없으면
COPY src /app/src                     # MISS: 소스 변경 시만
RUN  cd /app && ./gradlew build       # MISS: 소스 변경 시만

Docker Daemon 역할

Docker Daemon(dockerd)은 Docker 시스템의 중앙 관리자입니다. CLI 요청을 받아 컨테이너·이미지·볼륨·네트워크를 실제로 관리합니다.

CLIENT → DAEMON → RUNTIME 흐름
docker CLI
docker run / build ...
──REST──▶
dockerd
Docker Daemon
──gRPC──▶
containerd
Container Runtime
/var/run/docker.sock
프로세스 계층
dockerd (Docker Daemon)
  └─ containerd              # 컨테이너 생명주기 관리
       ├─ containerd-shim     # 컨테이너당 1개 — 데몬 재시작 시 컨테이너 보존
       │    └─ runc           # OCI 표준 컨테이너 생성 후 종료
       │         └─ your app process
       └─ BuildKit            # 병렬 이미지 빌드
💡 containerd-shim의 역할 dockerd가 재시작되어도 실행 중인 컨테이너가 죽지 않는 이유입니다. shim이 컨테이너 프로세스의 부모 역할을 유지해 데몬과 컨테이너를 분리합니다.

07

Kernel Space / User Space

OS는 실행 권한 수준에 따라 두 영역으로 나뉩니다. CPU 자체가 하드웨어적으로 이 두 모드를 구분합니다.

🟢 User Space (Ring 3)
  • 일반 앱이 실행되는 영역
  • Chrome, Java 앱, bash 등
  • 하드웨어에 직접 접근 불가
  • 메모리 주소 공간이 제한됨
  • 잘못 동작해도 시스템 전체 안전
🔴 Kernel Space (Ring 0)
  • OS 커널이 실행되는 영역
  • 최고 권한 — 모든 하드웨어 접근 가능
  • 메모리·CPU·디스크·네트워크 직접 제어
  • 여기서 버그 나면 시스템 전체 크래시
  • 일반 프로세스는 진입 불가
💡 Docker와의 연결 컨테이너 안의 앱이 syscall을 날리면 그것을 처리하는 커널은 호스트의 것입니다. VM은 Guest OS 커널이 별도로 있어서 Guest 커널이 먼저 받습니다. 이것이 "커널 공유"의 실체입니다.
08

시스템 콜 (System Call)

앱이 파일 읽기·네트워크·메모리 할당 등 하드웨어 자원이 필요할 때 커널에 요청하는 유일한 통로입니다.

syscall 흐름
[ User Space — Ring 3 ]
App 코드 실행 중... 파일을 읽어야 함 → open("/etc/config") 호출
⬇ syscall 발생 — CPU 모드 전환 (Ring 3 → Ring 0)
[ Kernel Space — Ring 0 ]

부팅 과정 — 커널을 메모리에 올리는 것

부팅의 본질은 커널 이미지를 디스크에서 RAM에 올리고 초기화하는 것입니다.

STEP 1
전원 ON → BIOS/UEFI 실행
CPU가 ROM 칩의 고정 주소를 읽음. 펌웨어가 CPU·RAM·장치 초기화(POST). OS 없이 동작
ROM 펌웨어
STEP 2
부트로더(GRUB) 실행
BIOS가 디스크 MBR/GPT에서 부트로더를 찾아 RAM에 올림. 어떤 OS를 부팅할지 선택
HDD/SSD
STEP 3 ★
커널 이미지 → RAM 로드 (핵심)
vmlinuz(압축 커널 ~10~14MB)를 디스크에서 RAM으로 복사. 압축 해제 후 커널 자기 초기화
RAM에 적재
STEP 4
커널 초기화
메모리 관리자·스케줄러·드라이버 세팅. initramfs로 루트 파일시스템 마운트
Kernel Space
STEP 5
PID 1 실행 → 서비스 기동
커널이 systemd를 최초 프로세스로 실행. 이후 모든 서비스·데몬 병렬 시작
User Space

왜 요즘 부팅이 빠른가

⚡ systemd 병렬 기동
  • 구형 SysV init: 서비스를 순차 실행
  • systemd: 의존성 분석 후 병렬 실행
  • 필요 없는 서비스는 지연 로딩
💾 NVMe SSD 보급
  • HDD 순차 읽기: ~150 MB/s
  • NVMe 순차 읽기: ~3,500 MB/s
  • 커널 30MB 로드가 거의 순간
🪟 Windows Fast Startup
  • 종료 시 커널 상태를 파일에 저장
  • 다음 부팅 시 RAM에 복원
  • 엄밀히는 재부팅이 아닌 복원
✅ Docker가 밀리초에 뜨는 이유 커널은 이미 RAM에 올라가 있습니다. 컨테이너는 STEP 1~4가 전혀 없고, Namespace + cgroup 설정 후 프로세스 하나를 실행하는 것뿐입니다.

Hypervisor란

VM을 만들고 관리하는 전용 소프트웨어 계층입니다. Host OS에 포함된 것도 아니고, 일반 앱의 기능도 아닙니다.

물리 하드웨어(CPU, RAM, 디스크)를 여러 VM이 나눠 쓸 수 있도록 가상 하드웨어를 만들어 각 VM에 제공합니다.

Type 1 vs Type 2

Type 1 — Bare-metal Hypervisor
  • 하드웨어 위에 Hypervisor만 올라감
  • 범용 Host OS가 아예 없음
  • Hypervisor 자체가 OS 역할 일부 수행
  • 성능 우수, 주로 서버·데이터센터용
Type 2 — Hosted Hypervisor
  • 범용 Host OS 위에서 앱처럼 실행
  • Host OS가 반드시 존재
  • CPU 가상화 명령어(VT-x)를 활용
  • 주로 개발자 노트북·개인 환경

VirtualBox vs KVM/QEMU 비교

📦 VirtualBox on Linux
  • 자체 하이퍼바이저 엔진(VBoxVMM) 사용
  • KVM 모듈과 무관하게 동작
  • CPU 가상화 명령어(VT-x)는 직접 사용
  • Type 2 Hypervisor
  • GUI 친화적, 개발자 노트북용
⚙️ KVM + QEMU on Linux
  • KVM 커널 모듈로 CPU 가속
  • QEMU가 나머지 하드웨어 에뮬레이션
  • 성능이 VirtualBox보다 우수
  • Type 2 (엄밀히) / 업계에서 Type 1.5
  • 서버·클라우드 환경에 적합
⚠️ VirtualBox + KVM 동시 실행 시 충돌 KVM은 /dev/kvm 을 통해 CPU 하드웨어 가상화 명령어(VT-x/AMD-V)를 독점적으로 사용하려 합니다. VirtualBox도 같은 명령어를 직접 쓰려 하기 때문에, 두 소프트웨어를 동시에 실행하면 충돌이 발생합니다. VirtualBox 실행 전 KVM 모듈을 언로드해야 합니다.
KVM ↔ VirtualBox 전환
# KVM 모듈 언로드 (VirtualBox 사용 전)
$ sudo modprobe -r kvm_intel   # Intel CPU
$ sudo modprobe -r kvm_amd    # AMD CPU
$ sudo modprobe -r kvm

# KVM 모듈 다시 로드 (KVM/QEMU 사용 시)
$ sudo modprobe kvm
$ sudo modprobe kvm_intel

KVM — Linux 커널 가상화

KVM(Kernel-based Virtual Machine)은 Linux 커널 안에 내장된 가상화 모듈입니다. 독립 실행 프로그램이 아니라 커널 모듈입니다.

✅ KVM이 하는 것
  • CPU 명령어 가상화
  • 메모리 가상화
  • /dev/kvm 인터페이스 제공
  • CPU 하드웨어 가상화 명령어 활용 (VT-x, AMD-V)
❌ KVM이 못 하는 것
  • 가상 디스크
  • 가상 네트워크 카드
  • 가상 USB · 그래픽 카드
  • BIOS/UEFI 펌웨어
  • 스스로 VM을 띄우는 것
💡 KVM은 커널 모듈이라 혼자 VM을 띄울 수 없습니다 KVM은 /dev/kvm 이라는 인터페이스를 열어 "CPU 가상화 해줘"라는 요청을 받을 수 있을 뿐입니다. 누군가 이 인터페이스를 열고 명령을 내려야 하는데, 그 역할이 QEMU입니다.
16

QEMU — 하드웨어 에뮬레이터

하드웨어 전체를 소프트웨어로 통째로 흉내내는 에뮬레이터입니다. CPU, 디스크, 네트워크 카드, BIOS 등 VM에 필요한 모든 가상 하드웨어를 구현합니다.

🐢 QEMU 단독 (KVM 없이)
  • 모든 CPU 명령어를 소프트웨어로 번역
  • 매우 느림
  • 장점: x86 호스트에서 ARM Guest 실행 가능
  • 다른 아키텍처 에뮬레이션 가능
🚀 QEMU + KVM
  • CPU 명령어는 KVM이 하드웨어로 직접 실행
  • 나머지 하드웨어는 QEMU가 에뮬레이션
  • 빠름 (네이티브에 근접)
  • 단점: 호스트와 같은 아키텍처만 가능
