JWT 해부도
JSON Web Token

JWT는 암호화된 상자가 아니라,
서명이 붙은 투명한 영수증이다.

JWT(JSON Web Token)는 서버가 "이 사용자는 이런 권한을 가진다"는 주장(claim)을 발급 시점에 서명해 봉인한 문자열입니다. 서버는 이후 이 문자열을 다시 열어보지 않고도 서명만 검증해서 위조 여부를 판단합니다. 아래에서 실제로 이 문자열이 어떻게 세 조각으로 쪼개지고, 어떻게 서명되고, 어떻게 변조가 감지되는지 하나씩 뜯어봅니다.

01 — Structure

세 조각의 역할

JWT는 .(마침표) 두 개로 구분된 세 부분으로 구성됩니다. 각 부분은 Base64Url로 인코딩된 JSON입니다(서명 제외).

① Header 
{
  "alg": "HS256",
  "typ": "JWT"
}

서명에 어떤 알고리즘을 썼는지 명시. 검증하는 쪽은 이 값을 신뢰하지 않고 자신이 기대하는 알고리즘과 일치하는지 검사해야 합니다 (07번 항목 참고).

② Payload 
{
  "sub": "1234",
  "name": "김민수",
  "role": "user",
  "iat": 1710000000,
  "exp": 1710003600
}

실제 주장(claim)이 담기는 곳. 등록 클레임(sub, exp 등)과 커스텀 클레임을 함께 넣습니다.

③ Signature 
SHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)

헤더와 페이로드를 이어붙인 문자열을 비밀키(또는 개인키)로 서명한 값. 페이로드 내용이 한 글자라도 바뀌면 서명 값이 완전히 달라집니다 — 이게 JWT 무결성 검증의 핵심입니다.

02 — 흔한 오해

Base64Url은 암호화가 아니다

Header와 Payload는 인코딩되어 있을 뿐 암호화되어 있지 않습니다. 누구나 브라우저 콘솔에서 atob() 한 줄로 그대로 읽을 수 있습니다. 서명은 "내용을 숨기는" 용도가 아니라 "발급 이후 내용이 바뀌지 않았음을 증명하는" 용도입니다.

따라서 비밀번호, 주민등록번호, 카드번호 같은 민감정보를 Payload에 절대 넣지 마세요. 누구든 토큰만 가로채면 base64 디코딩으로 그대로 읽어낼 수 있습니다.
03 — Algorithms

대칭키() vs 비대칭키( / )

서명 방식에 따라 "누가 토큰을 발급할 수 있는가"와 "누가 검증만 할 수 있는가"가 달라집니다.

— 대칭키()

  • 발급자와 검증자가 동일한 비밀키를 공유
  • 키를 아는 쪽은 발급도, 검증도, 위조도 가능
  • 서버 하나 또는 신뢰할 수 있는 내부 서비스 간에 적합
  • 구현이 단순하고 연산이 빠름

/ — 비대칭키

  • 발급자는 또는 타원곡선 알고리즘의 개인키로 서명, 검증자는 공개키로 검증만 가능
  • 검증 서버가 여러 개고 서로 신뢰 수준이 다를 때 유리 (MSA, 외부 파트너 API)
  • 공개키가 유출돼도 위조 서명은 만들 수 없음
  • 연산 비용이 보다 큼
실무 기준 — 검증 주체가 하나뿐이고 신뢰 경계 안이면 으로 충분합니다. 여러 마이크로서비스나 제3자가 "검증만" 해야 한다면 /로 발급자와 검증자의 권한을 분리하세요.
04 — Under the hood

해시 함수, 그 안에서는 무슨 일이 일어나는가

HS256, RS256, ES256 — 이름 뒤에 붙은 "256"은 전부 같은 것을 가리킵니다. 바로 해시 함수입니다. 세 알고리즘의 차이는 사실 "해시를 낸 다음, 그 해시를 어떻게 서명으로 바꾸는가"에서 갈립니다. 먼저 해시 자체가 내부적으로 뭘 하는지부터 뜯어봅니다.

SHA-256이 밟는 6단계

  1. 패딩(Padding) — 메시지 끝에 1 비트 하나를 붙이고 그 뒤를 0으로 채워서, 마지막 64비트를 뺀 나머지 길이가 512의 배수가 되게 만듭니다. 마지막 64비트에는 원본 메시지의 길이(비트 수)를 그대로 적어 넣습니다.
    원본 메시지 패딩 시작 비트(1) 패딩 0 길이(64bit)
  2. 512비트 블록 분할 — 패딩이 끝난 메시지를 512비트(64바이트)짜리 블록 N개로 자릅니다.
    블록 1
    블록 2
    블록 3
    …
    블록 N
  3. 메시지 스케줄 확장 — 2번에서 나온 512비트(64바이트) 블록 하나를, 32비트(4바이트)씩 16조각으로 쪼갠 게 W0~W15입니다 (32비트 × 16개 = 512비트 = 64바이트 — 블록 하나와 정확히 같은 크기이고, 그냥 잘라서 이름만 붙인 것뿐입니다). 이 16개를 함수로 굴려가며 64개의 워드(W0~W63)로 늘립니다.
    32비트 × 16 = 512비트(64바이트) — 블록 하나와 같은 크기
  4. 작업 변수 초기화 — 새로 계산하는 단계가 아니라 복사해오는 단계입니다. 64라운드 동안 뒤섞일 8개의 그릇(a~h)에, 직전 블록까지 누적된 해시값(H0~H7)을 그대로 옮겨 담습니다(a=H0, b=H1, … h=H7). 첫 블록이라 "직전 결과"가 없으면 처음 8개 소수(2,3,5,7,11,13,17,19)의 제곱근 소수부에서 뽑아낸 고정 상수를 대신 씁니다. 이 연결고리 때문에 앞쪽 블록이 하나만 바뀌어도 뒤 블록 전체의 계산이 도미노처럼 달라집니다.
    이전 블록의 누적값 H0~H7 (각 32비트, 총 256비트) — 또는 첫 블록이면 고정 상수

  5. 64라운드 압축 — 라운드마다 워드 1개(Wt)와 고정 상수 1개(Kt)만 새로 들어옵니다. a~h를 절반씩 나눠서 T1, T2 두 값을 먼저 계산한 다음, a~h 전체를 한 칸씩 밀며 그 자리에 새 값을 채웁니다. T1이 "갑자기" e 자리에 들어가는 게 아니라, T1 자체가 원래 e·f·g·h로 계산된 값이라 e 라인에 다시 흘러들어가는 게 자연스러운 흐름입니다 — 아래에서 순서대로 따라가 보세요.

왜 되돌릴 수 없나 — 각 라운드는 정보를 계속 섞고 뭉개는 다대일 연산입니다. 출력 256비트만 보고 64라운드 전의 입력 상태를 역산할 방법이 수학적으로 알려져 있지 않습니다.
왜 a~h에서 한 번에 끝내지 않나 — 압축 로직 자체는 512비트짜리 블록 1개만 처리할 수 있게 설계돼 있습니다. 메시지가 그보다 길면 블록을 여러 개로 나눠야 하는데, 블록마다 따로 계산하면 "메시지 전체의 해시"가 아니라 "블록별 해시 여러 개"가 되어버립니다. 그래서 H0~H7이라는 누적 상태를 다음 블록으로 넘겨받아 이어서 계산합니다 — 여러 자릿수를 손으로 더할 때 자리마다 올림(carry)을 넘기는 것과 같은 원리입니다.

직접 해시해보기 — 눈사태 효과

아래 두 입력은 글자 하나만 다릅니다. 실제 SubtleCrypto로 SHA-256을 계산해서 출력이 얼마나 달라지는지 확인해보세요.

서명 알고리즘마다 해시를 쓰는 방식이 다르다

해시값 자체는 셋 다 SHA-256으로 똑같이 만듭니다. 그 다음이 다릅니다.

HMAC (HS256)

H((K'⊕opad) ‖ H((K'⊕ipad) ‖ m))

비밀키 K를 블록 크기에 맞춰 패딩한 뒤, 고정 상수 ipad/opad와 XOR해서 해시를 두 겹으로 감쌉니다. 겹쳐 해싱하는 이유는 해시 함수 단독의 알려진 취약점(길이 확장 공격)을 원천 차단하기 위해서입니다.

RSA (RS256)

c = pad(H(m))^d mod n

메시지를 해시한 값에 PKCS#1 패딩을 씌우고, 그 정수를 개인키 지수 d로 거듭제곱합니다. 검증자는 공개키 지수 e로 다시 거듭제곱해 패딩을 벗기고, 자신이 계산한 해시와 비교합니다.

ECDSA (ES256)

k → (r, s) on curve P-256

해시값을 정수로 바꾼 뒤, 매번 새로 뽑는 난수 k로 타원곡선 위의 점 연산을 해 서명쌍 (r, s)를 만듭니다. 같은 메시지라도 서명할 때마다 다른 값이 나오지만, 둘 다 유효합니다.

ECDSA의 함정 — 서명마다 쓰는 난수 k가 재사용되거나 예측 가능하면 개인키가 통째로 역산됩니다. 2010년 소니 PlayStation 3의 코드 서명이 뚫린 사고가 바로 이 실수(모든 서명에 같은 k를 사용) 때문이었습니다.

05 — End to end

로그인부터 리소스 응답까지

1클라이언트가 ID/PW로 로그인 요청
→
2서버가 인증 후 JWT 생성 & 서명
→
3클라이언트가 토큰 저장 (쿠키/메모리)
→
4이후 요청마다 Authorization: Bearer <token>
→
5서버가 서명 검증 + exp/aud/iss 확인
→
6유효하면 요청 처리, 아니면 401

중요한 점: 서버는 3~6단계에서 세션 스토리지를 조회하지 않습니다. 서명 검증만으로 신뢰 여부를 판단하기 때문에 stateless합니다 — 이것이 JWT가 확장성 좋은 인증 방식으로 불리는 이유입니다.

08 — Security

실무에서 자주 터지는 함정

① alg:none / 알고리즘 다운그레이드 공격

공격자가 Header의 alg를 none으로 바꾸고 서명을 빈 문자열로 만들어 보내는 공격. 검증 로직이 토큰이 스스로 주장하는 alg 값을 그대로 신뢰하면 서명 검증을 건너뛰게 됩니다.

대응 — 검증 시 알고리즘을 화이트리스트로 고정하세요 (예: "나는 만 허용한다"). 라이브러리 설정에서 허용 알고리즘을 명시적으로 지정하는 옵션을 반드시 사용합니다.

② 약한 Secret에 대한 무차별대입

의 secret이 짧거나 예측 가능하면 오프라인에서 brute-force로 뚫릴 수 있습니다. secret은 최소 256비트 이상의 충분히 랜덤한 값을 사용해야 합니다.

③ 저장 위치: localStorage vs httpOnly 쿠키

localStorage에 저장하면 XSS 공격 시 JS로 토큰을 그대로 탈취당할 수 있습니다. httpOnly + Secure 쿠키에 저장하면 JS 접근은 막을 수 있지만 대신 CSRF 방어(SameSite, CSRF 토큰)를 별도로 챙겨야 합니다. "완전히 안전한 저장소"는 없고, 위협 모델에 맞춰 트레이드오프를 선택하는 문제입니다.

④ 폐기(Revocation)가 원래 어렵다

JWT는 stateless가 장점이라, 서버가 "이 토큰 이제 무효야"라고 즉시 선언하기가 구조적으로 어렵습니다. 로그아웃해도 만료 전까지는 토큰 자체는 여전히 유효합니다.

대응 패턴 — 만료 시간을 짧게(수 분~수십 분) 잡고, 별도의 refresh token으로 재발급 구조를 만들거나, jti 기반 블랙리스트를 Redis 등에 두는 방식을 병행합니다.

⑤ Payload는 열람 가능하다는 전제로 설계

02번에서 다룬 내용의 반복이지만 실무에서 가장 흔한 실수라 다시 강조합니다 — 서명은 무결성만 보장하지, 기밀성은 보장하지 않습니다.

09 — Pattern

Access Token + Refresh Token

만료가 짧은 Access Token만으로는 매번 재로그인해야 하니 UX가 나빠집니다. 그래서 수명이 긴 Refresh Token을 별도로 발급해 조합합니다.

1로그인 시 Access(짧음) + Refresh(김) 동시 발급
→
2Access 토큰으로 평소 API 요청
→
3Access 만료되면 401 응답
→
4Refresh 토큰으로 재발급 엔드포인트 호출
→
5새 Access(필요시 새 Refresh) 발급

Refresh Token은 탈취 시 피해가 크므로 DB에 저장해 서버가 즉시 무효화할 수 있게 관리하는 경우가 많습니다 — 여기서는 stateless 원칙을 일부 포기하고 보안을 우선한 절충입니다.
