// Study Notes

Docker Layer 내부 구조

이미지가 어떻게 레이어로 쌓이고, Union Filesystem이 이를 하나의 뷰로 합치는지 기술적으로 이해한다.

// 01

Docker 이미지는 왜 "레이어"인가?

Docker 이미지는 단일 파일이 아니다. 변경 불가능한(immutable) 파일시스템 스냅샷 여러 개가 수직으로 쌓인 구조다. 각 레이어는 이전 레이어 대비 diff(변경분)만 저장한다.

컨테이너를 실행하면 그 위에 얇고 쓰기 가능한 레이어가 하나 더 올라간다. 이미지 레이어는 건드리지 않는다.

// 인터랙티브 레이어 스택 — 클릭하면 상세 설명
✏️
Container Layer
실행 중에만 존재 · 쓰기 가능
WRITABLE
컨테이너가 시작될 때 생성되는 임시 레이어. 프로세스가 파일을 쓰면 여기에 기록됨. 컨테이너 삭제 시 이 레이어도 사라짐. docker commit하면 이 레이어가 이미지로 굳음.
▲ Union Mount (OverlayFS)
⚙️
RUN apt-get install nginx
Layer sha256:a3f2... · 38MB
RO
Dockerfile의 RUN 명령 하나 = 레이어 하나. 명령 실행 후 파일시스템 변경분만 저장. sha256 해시로 식별되며, 같은 해시면 여러 이미지가 공유함.
📁
COPY ./app /app
Layer sha256:9c1e... · 12MB
RO
COPY / ADD 명령도 별도 레이어. 소스 파일이 1바이트라도 바뀌면 이 레이어부터 아래 모든 캐시가 무효화됨. 따라서 Dockerfile에서 COPY는 최대한 뒤에 배치하는 것이 캐시 효율에 좋음.
⚙️
RUN apt-get update
Layer sha256:7b8d... · 55MB
RO
패키지 인덱스를 갱신하는 레이어. apt-get update와 install을 같은 RUN에 묶지 않으면 update 레이어가 캐시되어 stale 패키지 문제가 생길 수 있음 (cache busting 패턴 참고).
🐧
FROM ubuntu:22.04
Base image · 77MB
BASE
모든 이미지의 출발점. FROM scratch는 진짜 빈 레이어. ubuntu:22.04 베이스 레이어는 Docker Hub에서 pull하며, 동일 레이어를 쓰는 다른 이미지들과 디스크를 공유함.
// 02

레이어는 기술적으로 어떻게 생성되나?

Docker 빌드 시 각 Dockerfile 명령은 임시 컨테이너를 실행하고, 그 컨테이너의 파일시스템 변경분을 tar로 묶어 저장한다. 이 diff가 곧 레이어다.

Dockerfile
FROM ubuntu:22.04 # Layer 0: base RUN apt-get update # Layer 1: /var/lib/apt/* 변경분만 저장 RUN apt-get install -y nginx # Layer 2: /usr/sbin/nginx 등 추가 COPY ./html /var/www/html # Layer 3: /var/www/html/* 추가 CMD ["nginx", "-g", "daemon off;"] # 메타데이터만, 레이어 생성 안 함

// 내부에서 실제로 일어나는 일

🔨
1. exec 임시 컨테이너

이전 레이어들을 읽기 전용으로 마운트한 환경에서 명령 실행

📸
2. 파일시스템 diff 추출

명령 전후의 파일시스템을 비교해 추가/수정/삭제된 파일만 추출

📦
3. tar 아카이브로 저장

diff를 tar.gz로 압축, sha256 해시 계산 후 content-addressable store에 저장

🔗
4. manifest에 연결

이미지 manifest JSON에 레이어 해시 목록을 순서대로 기록

// 레이어 해시 체인

각 레이어는 sha256으로 식별되고, 이미지 manifest가 이들을 순서대로 묶는다.

BASE sha256:7b8d…
→
RUN update sha256:a3f2…
→
RUN install sha256:9c1e…
→
COPY sha256:f55a…
→
IMAGE ID sha256:1d2c…
// 03

Union Filesystem — 레이어를 하나로 합치는 기술

여러 레이어(디렉터리)를 하나의 파일시스템처럼 보이게 마운트하는 기술이 Union Filesystem이다. Linux에서는 OverlayFS가 표준으로 사용된다.

📁 merged (컨테이너가 보는 뷰) ← 실제 접근 경로
↑ Union Mount
upperdir (Container RW) 쓰기 발생 시 여기에 기록
+
workdir (OverlayFS 내부) CoW 임시 작업 디렉터리
↑
lowerdir[2]Layer N
lowerdir[1]Layer N-1
lowerdir[0]Base Layer

// OverlayFS mount 명령 예시

$ mount -t overlay overlay \ -o lowerdir=/layer0:/layer1:/layer2,\ upperdir=/container/rw,\ workdir=/container/work \ /container/merged # lowerdir: 읽기 전용 이미지 레이어들 (콜론으로 구분, 오른쪽이 최상위) # upperdir: 컨테이너 전용 쓰기 레이어 # merged : 컨테이너 프로세스가 실제로 보는 경로

// 파일 조회 우선순위

같은 경로의 파일이 여러 레이어에 있을 때, upperdir → 최신 lowerdir → 구 lowerdir 순으로 가장 위 레이어의 파일을 반환한다. 삭제는 whiteout 파일(.wh.<filename>)로 표시해 하위 레이어 파일을 가린다.

시나리오동작결과 위치
파일 읽기 (수정 없음)lowerdir에서 직접 참조lowerdir (복사 없음)
파일 수정lowerdir → upperdir로 CoW 복사 후 수정upperdir
파일 삭제upperdir에 whiteout 파일 생성upperdir (.wh.파일명)
새 파일 생성upperdir에 직접 생성upperdir
// 04

Copy-on-Write (CoW) 메커니즘

이미지 레이어는 read-only다. 컨테이너가 파일을 수정하려 할 때 비로소 복사가 일어난다. 이것이 Copy-on-Write다. 읽기만 한다면 복사 비용은 제로다.

// CoW 실행 흐름 — nginx.conf 수정 시나리오

1
컨테이너가 /etc/nginx/nginx.conf 수정 요청. 현재 파일은 lowerdir(이미지 레이어)에 존재.
2
OverlayFS가 해당 파일을 upperdir(컨테이너 RW 레이어)로 복사. (이미지 레이어는 그대로)
3
복사된 upperdir의 파일에 수정 내용 기록. 이미지 레이어의 원본은 변경되지 않음.
4
이후 조회 시 upperdir 파일이 우선 반환됨. 동일 이미지를 쓰는 다른 컨테이너는 영향 없음.

// CoW의 이점

⚡
빠른 컨테이너 시작

시작 시 이미지 전체를 복사하지 않음. 쓰기 발생 시에만 복사.

💾
디스크 공유

같은 이미지 기반의 컨테이너 100개가 이미지 레이어를 공유. 추가 용량 = 각 컨테이너의 변경분만.

🔒
이미지 불변성

이미지 레이어는 절대 수정되지 않으므로 무결성이 보장됨.

// 05

Storage Driver 종류

Union Filesystem을 구현하는 방식은 여러 가지다. 현재 Linux에서는 overlay2가 기본 표준이다.

Driver 기반 기술 권장 여부 특이사항
overlay2 OverlayFS (kernel 4.0+) ✓ 현재 표준 성능 우수, 커널 내장
overlay OverlayFS (구버전) ✗ deprecated inode 소진 문제 있음
devicemapper LVM thin provisioning ✗ deprecated RHEL/CentOS 구버전 사용
btrfs Btrfs subvolume/snapshot △ 선택적 Btrfs 파일시스템 필요
zfs ZFS dataset △ 선택적 ZFS 파일시스템 필요
vfs 단순 디렉터리 복사 ✗ 비추천 CoW 없음, 테스트용

// 현재 Storage Driver 확인

$ docker info | grep "Storage Driver" Storage Driver: overlay2 $ docker inspect <container_id> | grep -A5 GraphDriver "GraphDriver": { "Data": { "LowerDir": "/var/lib/docker/overlay2/abc.../diff:...", "MergedDir": "/var/lib/docker/overlay2/abc.../merged", "UpperDir": "/var/lib/docker/overlay2/abc.../diff", "WorkDir": "/var/lib/docker/overlay2/abc.../work" } }
// 06

레이어 캐시와 빌드 최적화

Docker는 빌드 시 각 명령의 레이어 해시를 로컬 캐시와 비교한다. 해시가 같으면 재실행하지 않고 캐시를 그대로 사용한다. 어느 레이어가 무효화되면 그 이후 레이어는 모두 재빌드된다.

// 나쁜 예 vs 좋은 예

✗ BAD — 소스 변경마다 전체 재빌드
FROM node:20 WORKDIR /app COPY . . # 소스 변경 → 캐시 bust RUN npm install # 매번 재실행됨 CMD ["node","app.js"]
✓ GOOD — 의존성은 캐시 활용
FROM node:20 WORKDIR /app COPY package*.json . # 의존성 파일만 RUN npm install # 캐시됨 COPY . . # 소스는 나중에 CMD ["node","app.js"]

// 레이어 수 줄이기 — RUN 명령 합치기

# 나쁜 예: 레이어 3개, apt 캐시가 별도 레이어에 남음 RUN apt-get update RUN apt-get install -y curl RUN rm -rf /var/lib/apt/lists/* # 좋은 예: 레이어 1개, 캐시 정리도 같은 레이어에서 RUN apt-get update \ && apt-get install -y curl \ && rm -rf /var/lib/apt/lists/*

// 레이어 수 확인 명령

$ docker history nginx:latest IMAGE CREATED CREATED BY SIZE 2ac752d7aeb1 2 weeks ago CMD ["nginx" "-g" "daemon…"] 0B <missing> 2 weeks ago STOPSIGNAL SIGQUIT 0B <missing> 2 weeks ago EXPOSE 80 0B <missing> 2 weeks ago COPY docker-entrypoint.sh … 4.62kB <missing> 2 weeks ago RUN /bin/sh -c set -x … 112MB ... $ docker inspect nginx:latest | python3 -c \ "import sys,json; d=json.load(sys.stdin); print(len(d[0]['RootFS']['Layers']),'layers')" 7 layers
// 07

이해도 확인 퀴즈

Q1. 컨테이너 내에서 이미지 레이어의 파일을 수정했다. 이미지 원본은?
A. 즉시 수정된다
B. 변경되지 않는다 (CoW로 upperdir에만 기록)
C. 컨테이너 종료 시 반영된다
D. 수정 자체가 불가능하다 (에러 발생)
✓ Copy-on-Write 덕분에 파일 수정 시도 시 해당 파일이 upperdir(컨테이너 레이어)로 복사된 후 수정된다. 이미지 lowerdir는 절대 변경되지 않는다.
Q2. Dockerfile에서 COPY . . 명령 이후 RUN npm install을 배치하면 생기는 문제는?
A. COPY 명령은 레이어를 생성하지 않아 문제없다
B. npm install이 병렬로 실행된다
C. 소스 파일이 1자라도 바뀌면 npm install 캐시도 무효화된다
D. node_modules가 이미지에 포함되지 않는다
✓ Docker 레이어 캐시는 순서 기반이다. COPY . . 레이어가 무효화되면 그 이하 모든 레이어(RUN npm install 포함)가 재실행된다. package.json을 먼저 복사하면 의존성이 변경될 때만 npm install이 재실행된다.
Q3. OverlayFS에서 컨테이너가 파일을 삭제할 때 실제로 일어나는 일은?
A. lowerdir에서 파일이 직접 삭제된다
B. 삭제가 불가능하다
C. upperdir에 whiteout 파일이 생성되어 lowerdir의 파일을 가린다
D. lowerdir의 파일이 upperdir로 복사된 후 삭제된다
✓ OverlayFS는 lowerdir를 절대 수정하지 않는다. 삭제 시 upperdir에 .wh.<filename> 형태의 whiteout 파일을 생성해 하위 레이어의 파일을 숨긴다. merged 뷰에서는 해당 파일이 없는 것처럼 보인다.
